Fork Guide

自分専用のチーム対戦
レーティングサイトを立ち上げる

GitHub・Supabase・Discord の3つを順につないでいきます。プログラミングの知識は要りません。 画面を見ながら値をコピーして貼り付ける作業が中心で、コマンドを打つ場面はありません。

所要時間
60〜90分
費用
無料
手順
全11ステップ
必要なもの
ブラウザだけ

  1. GitHub でコピーを作る
  2. Supabase でプロジェクトを作る
  3. Discord アプリを作る
  4. Supabase に Discord を登録
  5. 接続情報を登録する

はじめに

完成すると何ができるか

  • Discord アカウントでログインできる、自分だけのサイトが公開されます
  • 利用者はチームを作り、仲間を招待できます
  • 「マッチング」を押すと、実力の近いチーム同士が自動で対戦相手として組まれます
  • 勝敗を申告・承認すると、チェスと同じ Elo レーティング で強さの数値が更新されます
  • ランキングはログインしていない人でも見られます

使う3つのサービス

すべて無料で登録できます。Discord は既にお持ちの方が多いはずです。

サービス 役割 例えるなら
GitHub プログラムの保管庫。サイトの公開も行う 土地と建物
Supabase データの保管庫。ログインの窓口 倉庫と受付
Discord ログインに使う本人確認 身分証の発行元

作業の流れ

上から順に進めてください。順番を入れ替えないでください。後の手順で前の手順の値を使うためです。

  1. GitHub でコピーを作るサイトの住所が決まる
  2. Supabase でプロジェクトを作るデータの保管場所ができる
  3. Discord アプリを作るログインの仕組みができる
  4. Supabase に Discord を登録手順2と3をつなぐ
  5. 接続情報を登録するデータベースへの通り道を作る
  6. GitHub に設定値を登録手順2の値を GitHub へ渡す
  7. GitHub Pages を有効にする公開の準備
  8. 公開するサイトが動き出す
  9. 動作を確認する
  10. 自分を管理者にする
  11. 定期処理を有効にする

Step 01GitHub でコピーを作る

GitHub アカウントを作る

すでにお持ちの方は次へ進んでください。

  1. github.com/signup を開きます
  2. メールアドレス、パスワード、ユーザー名を入力します
  3. メールに届いた確認コードを入力します
Caution

ユーザー名はサイトの URL に入ります。後から変えると設定をやり直すことになるので、気に入った名前にしてください（半角英数字とハイフン）。

控えます。 → A GitHub ユーザー名（例 taro-yamada）

コピー（fork）を作る

「fork（フォーク）」は、他人のプログラムを自分の場所に丸ごとコピーする操作です。 コピー後は自由に触れます。元のプログラムには影響しません。

  1. 元のリポジトリを開きます
  2. 画面右上の Fork ボタンを押します
  3. Repository name は EloRating-MatchSystem のまま変えない
  4. Create fork を押します
Caution

公開設定はそのままに。fork したコピーは Public（公開）になります。Private（非公開）にすると、サイトの公開に GitHub の有料プランが必要になります。

公開されるのはプログラムだけです。利用者のデータは Supabase 側にあり、公開されません。

サイトの URL を控える

これがあなたのサイトの住所になります。まだ開いても何も表示されませんが、後で使います。 

https://<A>.github.io/EloRating-MatchSystem/

末尾のスラッシュまで含めてください。 → B サイトの URL

自動処理を有効にする

fork したコピーでは、自動処理（Actions）が最初は止まっています。

  1. 上部の Actions タブを開きます
  2. 黄色い案内の I understand my workflows, go ahead and enable them を押します

案内が出ない場合は、すでに有効です。

できたことの確認

Step 02Supabase でプロジェクトを作る

利用者の情報、チーム、試合結果などを保管する場所を用意します。

アカウントと組織を作る

  1. supabase.com を開きます
  2. Continue with GitHub を押すと、手順1のアカウントでそのまま登録できます
  3. 組織の作成を求められたら、好きな名前・Personal・Free で作ります

プロジェクトを作る

項目 設定
Name 好きな名前（例 elorating）
Database Password 強いパスワードを作る（下記参照）
Region Northeast Asia (Tokyo)
Danger

この画面を閉じるとパスワードは二度と表示されません。必ず今すぐ控えてください。

Generate a password で自動生成したものをコピーするのが確実です。自分で決める場合は、記号 @ : / ? # [ ] & を使わないでください。後の手順で URL の一部として扱うため、これらがあると正しく動きません。

→ E データベースのパスワード

Create new project を押します。準備に2〜3分かかります。

プロジェクトの情報を控える

Project Settings → Data API を開きます。

→ C Project URL（例 https://abcdefghijklmnopqrst.supabase.co）

この URL のうち、https:// と .supabase.co に挟まれた英小文字20文字が「project-ref」です。 

https://abcdefghijklmnopqrst.supabase.co
        ~~~~~~~~~~~~~~~~~~~~
        ここが project-ref

→ D project-ref

API キーを控える

Project Settings → API Keys を開きます。2種類あります。

名前 性質 控える先
Publishable key 公開してよい F
Secret key（sb_secret_...） 絶対に公開しない G
Danger

2つのキーの違いは重大です。

Publishable key は誰でも見られる前提の鍵です。サイトを開けば誰でも取り出せます。許される操作が制限されているため、公開されても問題ありません。

Service role key はすべての制限を無視できる鍵です。他人に知られると、全利用者のデータを自由に読み書き・削除されます。手順6で「Variables」の欄に間違って入れると全世界に公開されます。

アクセストークンを発行する

GitHub が Supabase を操作するための鍵です。プロジェクトの鍵とは別物です。

  1. アカウント設定の Access Tokens を開きます
  2. Generate new token を押し、名前を入れます（例 github-actions）
  3. 表示された sbp_ で始まる文字列を控えます

→ H アクセストークン

よくある間違い

ここで控えるのは アカウント設定 で発行した sbp_ で始まる値です。前項の API キーとは別物です。混同すると手順8で Invalid access token format というエラーで止まります。

できたことの確認

Step 03Discord アプリを作る

利用者が Discord アカウントでログインできるようにします。

アプリを作る

  1. Discord Developer Portal を開きます
  2. 右上の New Application を押します
  3. 名前を入れます。この名前は利用者のログイン画面に表示されます
  4. 利用規約に同意して Create を押します

戻り先を登録する

  1. 左メニューの OAuth2 を開きます
  2. Redirects → Add Redirect を押します
  3. 次を入力します
https://<D>.supabase.co/auth/v1/callback

画面下の Save Changes を押します。

Danger

戻り先はあなたのサイトの URL ではありません。Supabase の受付窓口の住所です。

利用者から見ると最後は自分のサイトに戻ってきますが、Discord が直接呼ぶのは Supabase の窓口だからです。ここに B を入れると redirect_uri mismatch というエラーになります。

Client ID と Secret を控える

同じ OAuth2 の画面にあります。CLIENT ID をコピーします。

→ I Discord Client ID（例 1234567890123456789）

Danger

Client ID は「数字」です。18〜19桁の数字であり、アプリの名前ではありません。

名前を控えてしまうと、手順4で登録してもログイン時に Discord が「無効なクライアント」というエラーを返します。数字の列であることを必ず確認してください。

続いて Reset Secret を押し、表示された文字列を控えます。

→ J Discord Client Secret

この画面を閉じると二度と表示されません。閉じてしまったら、もう一度 Reset Secret を押せば新しい値が出ます（古い値は無効になります）。

できたことの確認

Step 04Supabase に Discord を登録する

手順2と手順3をつなぎます。

Discord ログインを有効にする

  1. Authentication → Sign In / Providers を開きます
  2. 一覧から Discord を開き、Enable Sign in with Discord をオンにします
  3. Client ID に I、Client Secret に J を入れます
  4. Save を押します

戻り先を許可する

  1. Authentication → URL Configuration を開きます
  2. Site URL に B を入れます
  3. Redirect URLs に次を追加します
https://<A>.github.io/EloRating-MatchSystem/**

末尾のアスタリスク2つを必ず付けてください。サイト内のどのページへも戻れるようにするための書き方です。

Danger

ここを間違えると、エラーも出ずに変な場所へ飛ばされます。

登録が無い URL へ戻ろうとすると、Supabase はエラーを出さずに Site URL へ差し替えます。ログイン自体は成功しているのに localhost:3000 のようなまったく関係のない場所へ飛ばされる、という形で現れます。心当たりのない URL に飛ばされたら、まずこの画面を疑ってください。

Caution

広すぎる登録をしない。https://<A>.github.io/** のようにリポジトリ名を省いた形で登録すると、あなたの GitHub アカウントで公開している他のサイトすべてにログイン情報を渡せてしまいます。必ず /EloRating-MatchSystem/** まで含めてください。

できたことの確認

Step 05接続情報を登録する

プログラムがデータベースへ接続するための通り道を用意します。

接続文字列を2種類取得する

Project Settings → Database → Connection string を開きます。タブが並んでいるので、Session pooler と Transaction pooler の2つをそれぞれコピーします。 

postgresql://postgres.<D>:[YOUR-PASSWORD]@aws-0-ap-northeast-1.pooler.supabase.com:5432/postgres

[YOUR-PASSWORD] の部分を E に置き換えます。角カッコも消してください。

種類 末尾のポート 控える先
Session pooler :5432 K
Transaction pooler :6543 L
Caution

違いはポート番号だけです。取り違えないよう、番号を確認してから控えてください。

また、ホスト名が .pooler.supabase.com であることを確認してください。db.<D>.supabase.co という形のものは別の接続方法で、後の手順で失敗します。

Edge Function にシークレットを登録する

  1. Project Settings → Edge Functions を開きます
  2. Secrets → Add new secret を押します
  3. Name に APP_DB_POOL_URL、Value に L（:6543 の方）を入れます
  4. Save を押します
Caution

名前は一字一句正確に。SUPABASE_DB_URL という名前では登録できません。SUPABASE_ で始まる名前は Supabase が予約しているためです。

できたことの確認

Step 06GitHub に設定値を登録する

ここまでに集めた値を GitHub 側へ渡します。値の入れ場所が2種類あるので、間違えないでください。

種類 性質 ここに入れるもの
Variables 誰でも見られる サイトに埋め込まれる値
Secrets 登録後は本人にも見えない 秘密の値

自分のリポジトリの Settings → Secrets and variables → Actions を開きます。

Variables を3つ登録する

Name Value
VITE_SUPABASE_URL C Project URL
VITE_SUPABASE_ANON_KEY F Publishable key
VITE_BASE_PATH /EloRating-MatchSystem/
Caution

VITE_BASE_PATH は前後のスラッシュを両方付けてください。

  • EloRating-MatchSystem — 誤り（スラッシュ無し）
  • /EloRating-MatchSystem — 誤り（末尾のスラッシュ無し）

誤ると、サイトを開いても真っ白な画面になります。

Danger

ここに秘密の値を入れないでください。VITE_ で始まる値は、サイトを開いた人が誰でも読み取れます。これは仕組み上どうにもなりません。G Service role key をここに入れると全世界に公開されます。

Secrets を4つ登録する

Name Value
SUPABASE_ACCESS_TOKEN H（sbp_ で始まる）
SUPABASE_PROJECT_REF D（英小文字20文字）
SUPABASE_DB_PASSWORD E
SUPABASE_DB_URL K（:5432 の方）
よくある間違い
欄 入れるべきもの 間違えやすいもの
SUPABASE_ACCESS_TOKEN sbp_ で始まる値 API キー
SUPABASE_PROJECT_REF 英小文字20文字だけ URL 全体
SUPABASE_DB_URL ポート 5432 ポート 6543
できたことの確認

Step 07GitHub Pages を有効にする

  1. Settings → Pages を開きます
  2. Source を GitHub Actions に変更します

既定では「Deploy from a branch」になっています。変更するとその場で保存されます。

Danger

ここが「Deploy from a branch」のままだと、プログラムの元ファイルがそのまま配信され、真っ白な画面になります。サイトを開いて何も表示されないときは、まずここを確認してください。

できたことの確認

Step 08公開する

実行する

  1. Actions タブを開きます
  2. 左の一覧から Deploy を選びます
  3. 右側の Run workflow を押します
  4. 入力欄が出ます。何も変更せず、もう一度 Run workflow を押します
なぜ自動で公開されないのか

うっかり公開してしまうことを防ぐため、手動でボタンを押したときだけ公開する仕組みにしてあります。プログラムを変更しても、この操作をするまで公開中のサイトは変わりません。

待つ

処理には 8〜12分 かかります。次の順に進みます。

順番 名前 内容
1 verify プログラムに問題がないか検査する
2 backend データベースを準備する
3 frontend サイトを公開する

すべてに緑のチェックが付けば成功です。

失敗したとき

エラーに含まれる文字 原因 対処
Invalid access token format SUPABASE_ACCESS_TOKEN が sbp_ で始まっていない 手順2のトークン発行をやり直す
Invalid project ref format SUPABASE_PROJECT_REF に URL 全体を入れた 英小文字20文字だけにする
Network is unreachable SUPABASE_DB_URL が Pooler のものでない 手順5の Session pooler を入れ直す
password authentication failed パスワードが違う [YOUR-PASSWORD] の置換を確認

値を直したら、最初からやり直してください。何度実行しても問題ありません。

できたことの確認

Step 09動作を確認する

サイトを開く

B をブラウザで開きます。ランキング画面が表示されれば成功です。まだ誰もいないので中身は空です。

真っ白な場合は次を確認してください。

  • 手順7の Source が GitHub Actions になっているか
  • 手順6の VITE_BASE_PATH が /EloRating-MatchSystem/ になっているか
  • 公開直後は反映に数分かかります。10分ほど待ってから再読み込みしてください

ログインしてみる

右上の ログイン → Discord でログイン → Discord の確認画面で 認証。自分のサイトに戻ってダッシュボードが出れば成功です。

症状 確認する場所
「無効なクライアント」と出る 手順3の Client ID が数字か
redirect_uri mismatch と出る 手順3の Redirects
関係ない URL へ飛ばされる 手順4の Site URL と Redirect URLs

チームを作ってみる

マイチーム を開き、チーム名を入れて チームを作成。チーム名とレート 1500 が表示されれば、システムは正しく動いています。

できたことの確認

Step 10自分を管理者にする

管理者になると、システム設定の変更やチームの制限ができます。手順9で一度ログインしてから行ってください。

設定する

Supabase の SQL Editor を開き、New query に次を貼り付けます。 

UPDATE auth.users
   SET raw_app_meta_data = raw_app_meta_data || '{"role":"admin"}'::jsonb
 WHERE email = '<あなたのDiscordのメールアドレス>';

Run を押し、Success. 1 rows のような表示が出れば成功です。

0 rows と出た場合は、メールアドレスが違うか、まだ一度もログインしていません。次で確認できます。 

SELECT email FROM auth.users;

反映させる

Caution

一度ログアウトして、もう一度ログインしてください。権限はログイン時に発行される証明書に書き込まれるため、再ログインするまで反映されません。

ヘッダーに 管理 というリンクが増えていれば成功です。

できたことの確認

Step 11定期処理を有効にする

なぜ必要か

このシステムには、決まった時間ごとに自動で動く処理があります。

処理 内容
マッチング 待機中のチーム同士を組み合わせる
期限切れの処理 申告や承認が期限を過ぎた試合を自動で決着させる
お掃除 期限切れの招待や古い待機を消す
Danger

この手順を飛ばすと、静かに壊れます。

未設定でもエラーは出ません。しかし期限切れの試合が永久に終わらなくなり、そのチームは以後まったくマッチングできなくなります。エラーが出ないため気付きにくく、利用者から「対戦できない」と言われて初めて分かる、という形になります。

設定する

SQL Editor で次を実行します。2か所を自分の値に置き換えます。

SELECT vault.create_secret(
  'https://<D>.supabase.co/functions/v1',
  'edge_function_base_url'
);
SELECT vault.create_secret('<G:Secret key>', 'service_role_key');
Danger

鍵は sb_secret_ で始まる方です。同じ画面の Legacy API keys にある service_role（eyJhbG... で始まる長い文字列）ではありません。

見分けがつかない場合は実際に試すのが確実です。200 が返る方が正解です。 

curl -s -X POST https://<D>.supabase.co/functions/v1/matchmaker \
  -H "Authorization: Bearer <試す鍵>" -w " [%{http_code}]\n"

動いているか確認する

Danger

Cron の「成功」表示を信用しないでください。cron.job_run_details の succeeded が示すのは「SQL を実行できたこと」だけで、鍵が違って拒否されていても succeeded になります。

通信の結果そのものを見ます。設定から2分ほど待ってから実行してください。

SELECT status_code, left(content, 120) AS body, created
  FROM net._http_response
 ORDER BY created DESC
 LIMIT 5;
表示される番号 意味
200 成功。これが出れば完了です
403 鍵が違います。上の curl で正しい鍵を確かめてください
401 鍵が空か、形式が違います
何も出ない まだ登録できていません
できたことの確認

管理者の仕事

管理者としてログインすると、ヘッダーに 管理 が現れます。押すと3つの入口が並びます。

入口 できること
チーム管理 迷惑なチームのBANと解除
システム設定 人数・期限・レートの調整
監査ログ 誰が何をしたかの履歴

管理者を増やす

運営を複数人で行う場合、その人が一度ログインしてから SQL Editor で実行します。 

UPDATE auth.users
   SET raw_app_meta_data = raw_app_meta_data || '{"role":"admin"}'::jsonb
 WHERE email = '<管理者にする人のメールアドレス>';

対象者は一度ログアウトして再ログインすると反映されます。解除する場合は次のとおりです。 

UPDATE auth.users
   SET raw_app_meta_data = raw_app_meta_data - 'role'
 WHERE email = '<解除する人のメールアドレス>';
Caution

解除は即座には効きません。権限はログイン時に発行される証明書に書き込まれるため、その人がログアウトするまでは管理者として振る舞えます（最大1時間）。

急いで止める必要がある場合は、Supabase の Authentication → Users から対象者のセッションを失効させてください。

チームをBANする

不正や迷惑行為があったチームを、対戦に参加できない状態にします。

  1. 管理 → チーム管理 を開きます
  2. 上部の BANの理由 を入力します（1〜500文字・必須）
  3. 対象チームの BAN を押します
対象 BANするとどうなるか
マッチング 新しく待機に入れなくなる
待機中だった場合 その場で待機列から外れる
進行中の試合 そのまま続く。申告・承認は可能
ランキング 引き続き表示される
メンバー チームからは追い出されない

BANはチームに対する措置であり、個人アカウントの停止ではありません。メンバーはチームを脱退すれば、別のチームで活動できます。解除は同じ画面の 解除 を押すだけで、理由の入力は不要です。

Caution

入力した理由は監査ログに残り、後から編集も削除もできません。感情的な文言を書かず、第三者が見て判断できる事実を簡潔に記録してください。

良い例：2026-08-15 の対戦で虚偽申告。相手チームからの申告により確認
悪い例：迷惑

既にBANされているチームをもう一度BANしても、エラーにはなりません。解除も同様です。押しすぎて壊れることはありません。

記録は消せません

監査ログは追記だけの仕組みで、画面からも SQL からも編集・削除する手段を用意していません。誤ってBANした場合も、BANした記録と解除した記録の両方が残ります。運営の判断を後から検証できるようにするための設計です。

異常の通知を受け取る（推奨）

放っておくと、自動処理が止まっても誰も気付けません。エラーが表示されないためです。Discord へ通知が届くようにしておくと、利用者から苦情が来る前に対処できます。

手順1：Discord で受け取り口を作る

  1. 通知を受け取りたい Discord サーバーを開きます
  2. サーバー設定 → 連携サービス → ウェブフック → 新しいウェブフック
  3. 名前（例：EloRating 監視）と投稿先チャンネルを選びます
  4. ウェブフックURLをコピー を押します

管理者だけが見えるチャンネルを作って、そこへ投稿させるのがよいです。

手順2：GitHub へ登録する

リポジトリの Settings → Secrets and variables → Actions → Secrets で、DISCORD_WEBHOOK_URL という名前で登録します。

手順3：通知が届くか確かめる

  1. Actions タブ → 左から Monitor を選びます
  2. Run workflow を押し、そのまま Run workflow を実行します
  3. 1分ほどで Discord にメッセージが届きます
Caution

届かなければ、URLを登録し直してください。ここで確認しておかないと、本当に異常が起きたときに通知が来ないことに気付けません。

何が届くか

⚠️ EloRating: 異常を検知しました

・期限切れの試合が 3 件残っています（自動解決が止まっている可能性）
✅ EloRating: 今週も正常です（週次のお知らせ）

・期限切れの試合：なし
・チーム数：9
・直近7日の試合：確定 3 件 / 引き分け 1 件
Danger

毎週の連絡が来なくなったら、それが異常です。正常なときにも週1回お知らせが届くのは、通知の仕組み自体が壊れていないことを確かめるためです。「異常のときだけ知らせる」形にすると、通知が壊れたときに静かなまま気付けません。

月曜に連絡が来なかった週は、Actions タブを確認してください。なお GitHub は、リポジトリに60日間まったく変更が無いと自動処理を止めます。その場合も連絡が来なくなるので、同じように気付けます。

定期処理が止まっていないかの確認

最も多い原因です。SQL Editor で実行します。

SELECT jobname, status, start_time
  FROM cron.job_run_details
 ORDER BY start_time DESC
 LIMIT 20;

status が failed ばかり、または最近の行が無い場合は止まっています。手順11の Vault 登録を確認してください。

止まったままの試合を探す

SELECT id, status, report_deadline_at, approve_deadline_at
  FROM matches
 WHERE status IN ('PLAYING', 'WINNER_REPORTED')
 ORDER BY created_at;

期限を過ぎているのに残っている行があれば、定期処理が動いていません。

特定のチームの状態を調べる

SELECT name, rating, is_banned FROM teams WHERE name = '<チーム名>';

システム設定を変える

管理者としてログインし、ヘッダーの 管理 → 設定 を開きます。変えたい項目にだけ数値を入れて保存します。空欄の項目は変わりません。

変更は即座に全利用者へ反映されます。進行中の試合の期限は、その試合が作られた時点の設定で計算済みのため変わりません。次の試合から新しい値になります。

「拒否の上限回数」は無くなりました。拒否そのものを廃止したためです。画面にも出していません。効かない設定を並べておくと、調整すれば何か変わると誤解されるためです。

「保守による停止」だけは数値ではなくボタンです。現在が「停止中」か「稼働中」かが表示され、押すと切り替わります。ゲーム側の障害時は、これを先に立ててから進行中の試合を無効化してください。逆順にすると、無効化した直後に新しい試合が成立します。

シーズンの切替に関する状態はこの画面にありません。マッチングの停止・利用者操作の停止・現在のシーズン番号は、シーズンの操作だけが書き換えます。ここから触れてしまうと、シーズン切替の途中で状態を壊せるためです。

チーム人数の上限

この値がそのままマッチングに必要な人数になります。3 にすると、3人揃わないチームはマッチングを開始できません。2人対戦にしたい場合は 2 に変えてください。人数が揃っていないチームには、マッチング画面で「チーム人数が足りません」と表示され、開始ボタンが押せない状態になります。

1 にすると個人戦になります。 1人でチームを作り、そのまま対戦できます。このとき招待コードは発行できません（1人で既に定員に達しているためです）。

K値

大きくすると1試合での点数の動きが激しくなります。参加者が少なく早く序列を付けたい場合は大きめ（40〜48）、安定させたい場合は小さめ（16〜24）にします。

許容レート差

小さくすると実力の近い相手としか当たらなくなりますが、相手が見つかりにくくなります。参加チームが少ないうちは大きめ（600〜800）にしておくとマッチングが成立しやすくなります。

サブアカウント対策

同じ人が複数のアカウントを作り、身代わりのチームと対戦してわざと負けてレートを稼ぐことへの対策です。管理 → 設定 から調整します。

なぜ IP アドレスを見ないのか

同一の IP アドレスからの接続はサブアカウントとして疑わしく見えますが、採用していません。

  • VPN や、パソコンと携帯回線の使い分けで簡単に回避できます
  • 一方で家族・同居人・学校・LAN 会場・携帯電話会社の回線では、まったく無関係な人どうしが同じ IP アドレスになります

回避されやすく、しかも無実の人を巻き込む指標です。代わりに採ったのが上の2つの設定で、どちらも対戦の記録だけを見ています。誰が誰なのかを当てにいきません。だから VPN でも回線の使い分けでも効き目が変わりません。

疑わしい組み合わせを見る

管理 → 対戦の偏り の画面に、繰り返し当たっている組み合わせが並びます。

見るところ 意味
一方向性 100% は、一度も逆向きの結果が出ていないという意味
同時在席 重なり無し は、2つのチームが同じ時刻に別々の試合へ出たことが一度も無いという意味
集中 稼いだレートのうち、ひとりの相手から得た割合

「同時在席が重なり無し」が最も重要です。人はふたつのチームを同時に操作できません。IP アドレスを変えても、回線を分けても、この痕跡は消せません。

ただし、これは疑いであって証拠ではありません。仲の良い常連どうしも同じ形になります。参加者が少ないうちは特にそうです。画面には措置のボタンを置いていません。BAN やクールダウンは、通報の画面とチーム管理から、他の材料と突き合わせて判断してください。

検証のときは切ってください

自分で複数のアカウントを作って動作を確認したいときは、両方の設定を 0 にしてください。確認が終わったら戻すのを忘れないでください。

参加者が少ないうちは

「同じ相手と再戦できない長さ」が長すぎると、相手が見つからなくなります。参加チームが少ないうちは短くするか、0 にしてください。

待機している側にエラーは出ません。相手が見つからないまま待ち続けるだけなので、「マッチングが壊れた」と誤解されないよう、設定を変えたときは告知してください。

対戦カードを用意する

大会やイベントで、対戦する2チームを運営が直接指定できます。管理 → 対戦カードを用意する です。

自動マッチングとの違い

自動マッチング 対戦カードを用意する
相手の決まり方 レートの近さで自動 運営が指定
レート差の上限 あり（初期400） 無し
同じ相手との再戦 抑止される 抑止されない
回線相性による除外 される されない
クールダウン中のチーム 組まれない 組める
進行中の試合があるチーム 組まれない 重ねて組める

用意した試合の終わり方は普通の試合と同じです。投了・勝利申告・不成立の申請、どれも同じように使えます。レートも普通に動きます。

人数が揃っていなくても組めます

人数の違うチーム同士でも用意できます。自動マッチングと違い、ここでは止めません。画面に「人数が揃っていません」と出るので、承知のうえで組むか判断してください。大会では欠員のまま消化することがあるためです。レートは普通に動きます。

ただしメンバーが1人も居ないチームは組めません。誰も結果を報告できず、相手を申告期限まで待たせ続けることになるためです。

取り消せません

用意した試合を消すボタンはありません。誤って組んだ場合は、当事者どうしで「この試合は不成立」に合意してもらうか、管理 → 試合 から一括無効化してください。作成前に確認画面が出ます。

同じ組み合わせを何度でも

同じ2チームを繰り返し用意できます。3本勝負のような運用を想定しています。1本目が終わってから2本目を用意しても、同時に3本用意しても構いません。

用意できないとき

シーズンの切り替え中・メンテナンス中は用意できません。用意しても確定処理で打ち切られたり、ゲーム側が止まっていて対戦できなかったりするためです。BANされたチームも組めません。

シーズンを切り替える

管理 → シーズン の画面で行います。区切りをつけて、レートを初期値に戻す操作です。1回押して終わりではなく、順番に進みます。

① シーズンを終了する

シーズンを終了する を押すと、新しいマッチングの受付が止まります。進行中の試合はそのまま続けられます。対戦相手を巻き添えにしないためです。

このとき、チームを解散するかどうかも選べます。

選択 意味
通常のチームをすべて解散する BANされていないチームを削除します
BAN中のチームをすべて解散する BAN中のチームを削除します

どちらも選ばなければ、チームはそのまま残り、レートだけが戻ります。選ぶのはこの時点だけです。あとの工程は自動で進むため、後から選び直せません。

② 待つ（既定10分）

進行中の試合が決着するのを待ちます。この画面を開いたままにする必要はありません。

気が変わったら 終了を取りやめる を押せます。マッチングが再開します。ただし待っていた人の順番は戻らないので、押し直してもらう必要があります。

猶予が過ぎると、残っている試合は打ち切られて確定処理が自動で始まります。このとき利用者はチームの操作ができなくなります。

打ち切られた試合は「シーズンの終了により打ち切られました」と表示されます。レートは動かず、待機（クールダウン）も付きません。打ち切ったのは運営側であり、選手に落ち度が無いためです。

③ データを保存する

確定後、戦績データを保存 と ログデータを保存 が押せるようになります。CSVファイルがダウンロードされ、表計算ソフトで開けます。誰が何をしたかの情報は含まれません。

④ データを削除する（任意）

戦績とログを削除する を押すと、過去の試合記録が消えます。①でチームの解散を選んでいた場合、ここで一緒に削除されます。

元に戻せません。③で両方を保存していないと押せない仕組みにしてあります。消さなくても構いません。次のシーズンは問題なく始められます。

⑤ 通常営業に戻す

通常営業に戻す を押すと、利用者の操作とマッチングが再開します。これを押すまで利用者は何もできません。忘れないでください。

「保守による停止」が入っていると、これを押してもマッチングは動きません。意図した動作です。ゲーム側が直っていないのにマッチングが動き出さないようにしています。押す前に画面が注意します。復旧しているなら、管理 → 設定 で保守停止も解除してください。

障害がシーズンの切り替えと重なったとき

シーズンリセットの最中でも、保守停止・お知らせ・試合の一括無効化はそのまま実行できます。シーズンの切り替えに止められるのは選手側の操作だけです。

猶予中に対戦できなくなったら、試合を無効化してください。猶予は進行中の試合が終わるのを待つ時間です。障害で対戦できないまま放置すると、申告期限切れで解散し、両チームにクールダウンと不戦が付きます。当事者に落ち度はありません。一括無効化ならレートも記録も動きません。

過去のシーズンを見る

確定したシーズンは、画面上部の 過去のシーズン から誰でも見られます。そのときの順位・レート・勝敗が残ります。チーム名を選ぶと当時のメンバーも確認できます（メンバーの表示にはログインが必要です）。チームを解散しても、過去のランキングは残ります。

日々の運用

プログラムを最新にする

元のプログラムが更新されたとき、自分のコピーにも取り込めます。自分のリポジトリで Sync fork → Update branch を押し、手順8のデプロイを実行します。

何が変わるか分からない場合は急いで更新しないでください。今のまま動いているなら、それで問題ありません。

画面の変更だけを反映する

見た目だけを直した場合は、手順8の入力欄で 「バックエンドの適用を飛ばす」 にチェックを入れてください。データベースの処理を飛ばすため、5分ほどで終わります。

データのバックアップ

Supabase の Database → Backups から取得できます。無料枠では日次バックアップが7日分保持されます。大事なデータを扱う場合は、有料プランへの変更を検討してください。

困ったときは

症状 最初に見る場所
サイトが真っ白 手順7の Source、手順6の VITE_BASE_PATH
ログインできない 手順4の Client ID が数字か
ログイン後に変な URL へ飛ぶ 手順4の Site URL / Redirect URLs
「内部エラー」と出る 手順5の APP_DB_POOL_URL
チームは作れるが対戦が始まらない 手順11の定期処理
試合が終わらない 同上

やり直す

設定を間違えても、値を直して手順8のデプロイをやり直せば直ります。何度実行しても問題ありません。データが消えることもありません。

最初からやり直す

どうしても直らない場合は、Supabase のプロジェクトを削除して手順2からやり直すのが確実です。利用者のデータもすべて消えますので、公開前であることを確認してください。
