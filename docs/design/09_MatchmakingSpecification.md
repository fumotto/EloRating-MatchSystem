# Matchmaking Specification

Version: 3.0
Status: Active
Last Updated: 2026-08-27
準拠ADR: ADR-004, ADR-008, ADR-010, ADR-014, ADR-016, ADR-032, ADR-034, ADR-035, ADR-036

---

# 1. 目的

本書はチーム同士のマッチング仕様を定義する。

マッチングは固定チーム単位で実施する。

本書は以下の正本である。

* マッチング対象の条件
* 優先順位
* 許容レート差
* キューの運用

---

# 2. 基本仕様

| 項目      | 値                                         |
| ------- | ----------------------------------------- |
| マッチング単位 | チーム                                       |
| 許容レート差  | `system_settings.match_rating_range`（初期値 400） |
| 起動方式    | キュー登録時の同期試行 ＋ Cronによる救済実行                 |
| 待機方式    | キュー（`matching_queue`）                     |
| 同時参加    | **進行中の試合を持つチームは待機列に登録できない**（ADR-035）       |
| 優先順位    | レート差 → 待機時間 → Team ID                     |

許容レート差は設定値であり、コードへハードコードしない。

**★「1チーム同時1試合」という表現を用いない。** 規則は試合の本数ではなく**待機列への入り口**にある。
1チームが同時に複数の試合を持つことは、待機列を経由しない経路（将来の「管理者がマッチを用意する」運用）
では起こりうる（ADR-035 ①⑤）。

**保証はアプリケーション層のみで行う。DBに制約は無い**（ADR-035 ②③）。

---

# 3. マッチング対象

以下の条件をすべて満たすチームを対象とする。

| 条件            | 判定方法                                                  |
| ------------- | ----------------------------------------------------- |
| BANされていない     | `teams.is_banned = FALSE`                             |
| マッチ待機中である     | `matching_queue` にレコードが存在する                           |
| 進行中の試合が存在しない  | `matches` に `status NOT IN ('COMPLETED','DRAWN')` のレコードが無い |
| クールダウン中でない     | `teams.queue_cooldown_until` が NULL または過去（ADR-032 ④）        |
| 保守停止中でない       | `system_settings.maintenance_paused = FALSE`（ADR-034 ⑤）       |

チームに状態列は存在しない。「有効状態」「ACTIVE」といった状態名で判定してはならない（`03_Database.md` 7.3）。
クールダウン中かどうかも状態列を持たない。`queue_cooldown_until > NOW()` により導出する。

## 3.1 ペアの条件（ADR-034 ③）

上表はいずれも**単独のチーム**に対する条件である。これに加えて、**ペアに対する条件**が1つある。

```sql
AND NOT EXISTS (
  SELECT 1 FROM match_avoidance a
   WHERE a.expires_at > NOW()
     AND a.team_low_id  = LEAST(:team_id, :candidate_id)
     AND a.team_high_id = GREATEST(:team_id, :candidate_id)
)
```

回線相性のように**再現的に対戦が成立しないペア**を、繰り返しマッチさせないためのものである。
抑止が無ければ、同じペアが再びマッチして不成立を繰り返す。

加えて、**同じペアが短い間隔で繰り返し当たること**も抑止する（ADR-036 ①）。

```sql
AND NOT EXISTS (
  SELECT 1 FROM matches m
   WHERE m.status = 'COMPLETED'
     AND m.completed_at > NOW() - (:rematch_cooldown_hours || ' hours')::interval
     AND LEAST(m.team_a_id, m.team_b_id)    = LEAST(:team_id, :candidate_id)
     AND GREATEST(m.team_a_id, m.team_b_id) = GREATEST(:team_id, :candidate_id)
)
```

サブアカウントによるレートの水増しは、身代わりのチームと**繰り返し**当たることでしか成立しない。
頻度に上限を課すことが対策になる。**同一人物かどうかは判定しない。** 判定しないため、
VPN や回線の使い分けで回避できない（ADR-036 理由）。

**★対象は `COMPLETED` のみである。`DRAWN` を含めてはならない。** 抑止の目的はレートが動く試合の
反復を止めることであり、レートが動かない不成立を数える理由が無い。加えて ADR-034 は「落ち度の
無い側に代償を負わせない」と定めている。回線相性による再戦の抑止は `match_avoidance` が担う。

**★専用のテーブルを設けない。** `matches` から導出する。行を作らないため期限切れの掃除も要らない。

**★`rematch_cooldown_hours = 0` は無効を表す。** 検証環境ではこの値を 0 にする（ADR-036 ⑤）。

**★ペアの条件は待機列の絞り込みでは表現できない。** 単独チームの条件と異なり、相手が決まって初めて
判定できる。したがって候補の選択（`selectOpponent`、6章）の段階で判定する。上記2つの条件は
`runMatchmaking` が1つの除外集合へまとめ、`selectOpponent` へ渡す。

**★登録は合意による不成立（`MUTUAL`）かつ理由が `CONNECTION` の場合のみ**である。`NO_SHOW`（相手の沈黙に
よる成立）では登録しない。片方の操作で登録できると、強い相手を恒久的に回避する手段になる。

**★待機チーム数が少ない環境では、除外が組み合わせを枯渇させうる。** `avoidance_days`（初期30日）と
`max_avoidance_entries`（初期5）、および `rematch_cooldown_hours`（初期24時間）を運営が調整
できるようにしているのはこのためである。除外により相手が見つからないことはエラーではなく、
待機の継続である（4章）。

**★「待機が長引いたら再戦の抑止を緩める」という救済を入れてはならない**（ADR-036 備考）。
攻撃者はその時間を待てる。緩和は抑止そのものを無効にする。

**★管理者が用意する試合は本条件に拘束されない**（ADR-035 ⑤）。`match_avoidance` と
`queue_cooldown_until` はいずれも自動マッチングのための仕組みである。

# 4. マッチング開始

チームリーダーが「マッチング開始」を実行する。

```text
queue-match 呼び出し
  ↓
matching_queue へ登録
  ↓
マッチング処理を同期実行
  ↓
成立した場合は Realtime: MATCH_CREATED
成立しない場合は待機を継続（matched: false を返す）
```

待機中は重複してキュー登録できない（`QUEUE-001`）。

相手が見つからないことはエラーではない。`matched: false` を含む正常応答とする。

## 4.1 待機登録の条件

チームの人数が**必須人数に達していること**を要求する。満たない場合は `QUEUE-005` を返す。

必須人数は `system_settings.team_max_members` と等しい。専用の設定列は設けない。人数の異なるチーム同士を
対戦させないことが目的であり、必須人数と上限が一致していれば、待機列に入るチームはすべて同数になる。

判定は `queue-match` の中で、待機登録の直前に数え直す。招待の受諾や脱退は待機登録と独立に発生するため、
画面が表示した時点の人数を信用してはならない。

待機中に人数が減る経路は脱退のみであり、`leave-team` が `matching_queue` から当該チームを削除する。
したがって「必須人数を割ったまま待機し続ける」状態は生じない。

# 5. 起動方式

マッチング処理（`matchmaker`）は2つの契機で実行する。

| 契機          | 目的                            | 頻度       |
| ----------- | ----------------------------- | -------- |
| キュー登録時の同期実行 | 登録直後に相手が見つかれば即座に成立させる         | 登録のたび    |
| Cronによる救済実行 | 同期実行で取りこぼした組み合わせを成立させる        | 1分間隔     |

同期実行のみでは、次の場合に組み合わせが成立しないまま残る。

* 同期実行が競合により失敗した場合
* レート差の条件を満たす相手が、自チームの登録後に別の理由で待機解除・再登録された場合

Cronによる救済実行はこれを回収する。

# 6. マッチングアルゴリズム

## 6.1 手順

```text
1. advisory lock を取得（多重実行の防止）
2. 待機チームを取得（FOR UPDATE SKIP LOCKED）
3. 対象条件（3章）で絞り込む
4. system_settings から match_rating_range を取得
5. レート差が許容範囲内の候補を抽出
6. 優先順位で相手を決定
7. matches を作成し、両チームをキューから削除
```

## 6.2 優先順位

| 順位  | 基準           | 目的            |
| --- | ------------ | ------------- |
| 第1  | レート差が最も小さい   | 拮抗した対戦を優先する   |
| 第2  | 待機開始時刻が最も早い  | 長く待っているチームを優先 |
| 第3  | Team ID 昇順   | 同一条件時の決定性を保証  |

**レート差が第1優先である。** 待機時間で先に並べ替えてはならない。

## 6.3 レート差判定

```text
ABS(TeamA.rating - TeamB.rating) <= system_settings.match_rating_range
```

境界値（レート差が許容値とちょうど等しい場合）はマッチ対象に**含む**。

# 7. 同時実行制御

複数のリクエストが同時にマッチング処理を実行すると、同一チームが複数の試合に割り当てられる可能性がある。

これを防ぐため、以下を実施する。

## 7.1 アプリケーション側

```sql
-- マッチング処理全体を直列化する
SELECT pg_advisory_xact_lock(hashtext('matchmaking'));
```

または、対象行のみをロックする方式を用いる。

```sql
SELECT * FROM matching_queue
ORDER BY queued_at
FOR UPDATE SKIP LOCKED;
```

## 7.2 データベース側

アプリケーション側の制御が破られた場合の最終防御として、`matches` に部分UNIQUEインデックスを設ける（`03_Database.md` 10.6）。

```sql
CREATE UNIQUE INDEX ux_matches_active_team_a
  ON matches (team_a_id)
  WHERE status NOT IN ('COMPLETED', 'DRAWN');
```

同一チームが同時に2つの試合へ割り当てられた場合、INSERTが制約違反となりトランザクションがロールバックされる。

# 8. マッチ成立

マッチ成立時は以下を単一トランザクションで実施する。

```text
matches INSERT
  status = 'PLAYING'
  started_at = now()
  report_deadline_at = now() + system_settings.report_timeout_minutes
  ↓
matching_queue DELETE ×2
  ↓
audit_logs INSERT（MATCH_CREATED）
  ↓
COMMIT
  ↓
Realtime: MATCH_CREATED
```

## 8.1 生成される試合の状態

```text
PLAYING
```

マッチ成立と同時に試合が進行中となる（ADR-008）。

`MATCHED` および `IN_PROGRESS` は存在しない。試合開始という別の操作も存在しない。本システムは対戦管理を行うものであり、選手が実際にゲーム中であるかを判定できないためである。

## 8.2 チーム状態の更新は行わない

`teams.status` は存在しないため、マッチ成立時にチーム状態を更新する手順は存在しない。

進行中の試合の有無は `matches` から導出する。

---

# 9. マッチキャンセル

待機中のみキャンセルできる。

```text
cancel-match-queue 呼び出し
  ↓
matching_queue DELETE
```

マッチが成立した後はキャンセルできない。成立時点でキューから削除済みのため、キャンセル操作は `QUEUE-004`（マッチング待機中ではありません）となる。

成立した試合を取り消す手段はMVPでは提供しない。報告されないまま期限を迎えた場合は `DRAWN` として自動解散される（ADR-014）。

---

# 10. 待機の滞留対策

正常な処理では、待機情報は「マッチ成立」「キャンセル」「BAN」のいずれかで削除される。

想定外の滞留に備え、`cleanup-matching-queue`（Cron・10分間隔）が24時間以上経過した待機情報を削除する。

本処理で削除される件数は通常0件である。継続的に0でない場合は不具合の兆候として扱う。

# 11. Realtime通知

イベント名の正本は `04_BackendInterface.md` 7章である。

| 契機     | イベント            |
| ------ | --------------- |
| マッチ成立  | `MATCH_CREATED` |

キュー登録・キュー解除ではRealtime通知を送信しない。待機状態は自チームのみが参照するため、他クライアントへ通知する必要がないためである。

クライアントは通知受信後に必要なデータを再取得する。通知データを直接キャッシュへ書き込まない。

# 12. エラー

エラーコードの正本は `06_ErrorCode.md` である。本書に独自のコードを定義しない。

マッチングに関連する主なコード。

| Code      | 内容            |
| --------- | ------------- |
| QUEUE-001 | 既にマッチング待機中です  |
| QUEUE-002 | 試合中のため待機できません |
| QUEUE-003 | マッチング待機をキャンセルできません |
| QUEUE-004 | マッチング待機中ではありません |
| TEAM-005  | チームリーダーのみ実行できます |
| TEAM-006  | BANされたチームです   |

「マッチング可能な相手が見つからない」ことを表すエラーコードは存在しない。正常応答として `matched: false` を返す。

---


## 12.1 待機できない場合のコード（ADR-032 / ADR-034 / ADR-035）

| 状況                | コード         |
| ----------------- | ----------- |
| 既に待機中             | `QUEUE-001` |
| 進行中の試合がある         | `QUEUE-002` |
| 人数不足              | `QUEUE-005` |
| クールダウン中           | `QUEUE-006` |
| 保守による一時停止         | `QUEUE-007` |
| シーズン終了の猶予中        | `SEASON-002` |
| シーズン切替中           | `SEASON-001` |

**判定順は `04_BackendInterface.md` 21.8 に定める。** 停止中であることを人数不足より先に伝える。
利用者にとって「自分に直せない理由」を先に示すほうが親切であり、また人数を揃えてから停止を知るのは徒労である。

`QUEUE-006` のクールダウンは、誤魔化す経路を通ったチームにのみ課される。
**投了と承認による確定にはクールダウンが無い**（ADR-032 ④）。最短で次のキューへ入れるのが正直な道である。

# 13. 将来拡張

以下を将来の拡張として想定する。

* 待機時間に応じた許容レート差の拡大
* シーズン別マッチング
* ランク帯別マッチング
* 地域別マッチング
* マッチング辞退機能

許容レート差を `system_settings` の設定値としているのは、待機時間に応じた拡大を導入する際の変更範囲を小さくするためである。

---

## 13.1 管理者がマッチを用意する（ADR-035 ⑤ / ADR-039）— **実装済み**

**本節は将来拡張ではない。** `admin-create-match` として実装した（`04_BackendInterface.md` 12.11）。
将来拡張の一覧（13章）に残しているのは、本節が前提の正本であるためである。

自動マッチングを経由せず、管理者が対戦カードを直接作成する運用である。大会・イベントを想定する。

| 前提                | 内容                                                          |
| ----------------- | ----------------------------------------------------------- |
| 複数割り当て            | 1チームへ同時に複数の試合を割り当てられる                                       |
| 待機列               | 進行中の試合を持つ間、そのチームは `queue-match` から待機列へ入れない（規則は変わらない）        |
| `match_avoidance` | 拘束されない。抑止は自動マッチングのための仕組みである                                 |
| クールダウン            | 拘束されない。同上                                                   |
| 確定                | 通常の確定フロー（ADR-032）に従う。専用の確定手段は設けない                            |

**★`MatchmakingPage` は一覧前提へ改めた**（ADR-039 ⑧）。進行中の試合を単数として扱うと、
2件目以降が画面から消える。**1件でも一覧として出す。** 件数で表示の形を変えると、
2件目が現れたときに画面の意味が変わる。

### ADR-035 が触れていなかった条件（ADR-039 ③④）

上表の4つの前提は「何に拘束されないか」を定めたものである。以下は ADR-039 が加えて決めた。

| 条件                | 扱い                                        |
| ----------------- | ----------------------------------------- |
| `match_rating_range` | 拘束されない。実力の近い相手を探すための条件である              |
| 停止フラグ3種           | **従う。** 停止は全体の宣言であり、ペア単位・チーム単位の仕組みとは別物である |
| BANされたチーム         | 拒む（`TEAM-006`）                             |
| メンバー0人のチーム        | 拒む（`TEAM-011`）。誰も報告できず、相手を期限まで拘束する         |
| 必須人数              | **要求しない。** 待機列への入り口の条件であり（4.1）、本経路は待機列を経由しない |

# 14. AI実装ルール

* マッチング処理はキュー登録時に同期実行し、Cronで救済実行する。
* 優先順位は「レート差 → 待機時間 → Team ID」を厳守する。レート差を第1優先とする。
* 許容レート差は `system_settings.match_rating_range` から取得する。ハードコードしない。
* マッチ成立処理は単一トランザクションで実行する。
* advisory lock または `FOR UPDATE SKIP LOCKED` により同時実行を制御する。
* 生成する試合の状態は `PLAYING` とする。`MATCHED`・`IN_PROGRESS` を使用しない。
* `report_deadline_at` を必ず設定する。設定しないと自動解決バッチが対象を判定できない。
* チーム状態の更新処理を実装しない。`teams.status` は存在しない。
* Realtime通知では対象データを再取得させ、通知内容で直接更新しない。
