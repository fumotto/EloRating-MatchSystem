# Error Code Specification

Version: 2.0
Status: Active
Last Updated: 2026-08-03
準拠ADR: ADR-005, ADR-007, ADR-009, ADR-010, ADR-014

---

# 1. 目的

本書は、本システムで使用するエラーコードおよび共通レスポンス形式を定義する。

本書は以下の**唯一の正本**である（ADR-007、`ReferenceIndex.md`）。

* 共通レスポンス形式
* エラーコードとHTTPステータスの対応

他の設計書に独自のエラーコード一覧を定義してはならない。エラーコードを追加する場合は本書へ追加する。

エラーコードはフロントエンド、バックエンド、テストコード、ログ解析において共通で使用する。

---

# 2. 共通レスポンス形式

すべてのEdge Functionは `result` を含む共通形式で応答する（ADR-005）。

## 成功

```json
{
  "result": "OK",
  "data": {}
}
```

## 業務エラー

```json
{
  "result": "NG",
  "error": {
    "code": "TEAM-004",
    "message": "Team is full."
  }
}
```

## システムエラー

```json
{
  "result": "FATAL",
  "error": {
    "code": "SYSTEM-001",
    "message": "Internal server error."
  }
}
```

`success` 形式（`{"success": true}`）は使用しない。

`TEAM_NOT_FOUND` のようなSCREAMING_SNAKE形式のコードは使用しない。

# 3. HTTPステータス方針

| HTTP | 用途           |
| ---- | ------------ |
| 200  | 正常終了         |
| 400  | 入力値エラー       |
| 401  | 認証エラー        |
| 403  | 権限エラー        |
| 404  | 対象が存在しない     |
| 409  | 競合・業務ルール違反   |
| 500  | システムエラー      |

業務ルール違反はすべて **409** で表現する。422は使用しない。

「業務ルール違反」と「競合」を別ステータスへ分けると判定基準が曖昧になり、クライアント側の分岐が複雑になるためである。クライアントは `error.code` で処理を分岐する。

Edge Functions は本文の生成が常に成功するため、201・204は使用しない。作成・削除も200で応答する。

---

# 4. エラーコード命名規則

```text
<カテゴリ>-<3桁連番>
```

例

```text
AUTH-001
TEAM-003
MATCH-008
SYSTEM-001
```

## 4.1 テストIDとの区別

`10_TestSpecification.md` のテストIDは `TC-` を接頭辞に持つ（例 `TC-TEAM-001`）。

本書のエラーコードには接頭辞を付けない。両者は接頭辞の有無で機械的に判別できる。

# 8. Team

| Code     | HTTP | 内容                     |
| -------- | ---- | ---------------------- |
| TEAM-001 | 404  | チームが存在しません             |
| TEAM-002 | 409  | チーム名が重複しています           |
| TEAM-003 | 409  | 既にチームへ所属しています          |
| TEAM-004 | 409  | チーム人数が上限です             |
| TEAM-005 | 403  | チームリーダーのみ実行できます        |
| TEAM-006 | 409  | BANされたチームです            |
| TEAM-007 | 409  | 試合中のため脱退できません          |
| TEAM-008 | 409  | 先にリーダーを他のメンバーへ移譲してください |
| TEAM-009 | 409  | リーダーの移譲先が不正です          |
| TEAM-010 | 409  | チームに所属していません           |

`TEAM-005` はチームリーダー限定の操作（招待発行・キュー登録・リーダー移譲）で使用する。

`TEAM-008` は、他メンバーが存在するチームのリーダーが脱退しようとした場合に返す。単独メンバーのリーダーは脱退できる。

# 10. Match Queue

| Code      | HTTP | 内容            |
| --------- | ---- | ------------- |
| QUEUE-001 | 409  | 既にマッチング待機中です  |
| QUEUE-002 | 409  | 試合中のため待機できません |
| QUEUE-003 | 409  | マッチング待機をキャンセルできません |
| QUEUE-004 | 409  | マッチング待機中ではありません |
| QUEUE-005 | 409  | チーム人数が不足しています |
| QUEUE-006 | 409  | クールダウン中のため待機できません |
| QUEUE-007 | 409  | 保守中のため待機できません |

`QUEUE-002` は「進行中の試合を持つチームは待機列に登録できない」という規則である（ADR-035 ①）。
「1チーム同時1試合」ではない。**DBに制約は無く、本判定と `runMatchmaking` の除外条件が唯一の保証である。**

`QUEUE-006` はクールダウン中を示す（ADR-032 ④）。誤魔化す経路の代償は**レートではなく時間**で払わせる。
投了と承認による確定にはクールダウンを課さない。**最短で次のキューへ入れるのが正直な道である。**

`QUEUE-007` は保守による一時停止を示す（ADR-034 ⑤）。シーズン運用による停止（`SEASON-002`）とは
**別の列**で管理する。`admin-resume-season` が `matchmaking_paused` を無条件に解除するため、
兼用するとシーズン再開が保守停止を解除してしまう。

# 11. Match

| Code      | HTTP | 内容                    |
| --------- | ---- | --------------------- |
| MATCH-001 | 404  | 試合が存在しません             |
| MATCH-002 | 409  | 試合は既に終了しています          |
| MATCH-003 | 409  | 勝者は既に報告されています         |
| MATCH-004 | 409  | 勝者が報告されていません          |
| MATCH-005 | 403  | 試合への操作権限がありません        |
| MATCH-006 | 400  | 勝者チームの指定が不正です         |
| MATCH-007 | —    | **欠番**（`reject-match` の廃止により消滅・ADR-032 ②） |
| MATCH-008 | 409  | 他の操作と競合しました。再読み込みしてください |
| MATCH-009 | 409  | 自チームが申告した勝利には投了できません |
| MATCH-010 | 409  | 延長回数が上限に達しています |
| MATCH-011 | 409  | 保留中の申請があります |
| MATCH-012 | 409  | 申請回数が上限に達しています |

## 使用箇所

| コード       | 主な使用箇所                                                   |
| --------- | -------------------------------------------------------- |
| MATCH-002 | 状態が `COMPLETED` または `DRAWN` の試合に対するあらゆる操作                |
| MATCH-003 | 申告済みチームからの再報告、2度目の反対申告、`WINNER_REPORTED` での延長・不成立申請  |
| MATCH-004 | 状態が `PLAYING` の試合に対する承認                                   |
| MATCH-005 | 勝者チーム以外からの報告、敗者チーム以外からの承認、第三者による操作、申請者自身による応答      |
| MATCH-006 | `winnerTeamId` が当該試合の参加チームでない場合                          |
| MATCH-008 | 楽観ロック（`version`）の不一致                                     |
| MATCH-009 | `WINNER_REPORTED` で自チームが `winner_team_id` である場合の投了          |
| MATCH-010 | `report_extension_count` が `max_report_extensions` に到達          |
| MATCH-011 | 保留中の不成立申請があるうちの再申請                                        |
| MATCH-012 | `no_contest_request_count` が `max_no_contest_requests` に到達      |

`MATCH-008` は同時実行による競合を示す。クライアントは最新状態を再取得して操作をやり直す。

**`MATCH-007` は欠番である。** 「拒否回数が上限に達したため試合は解散されました」を割り当てていたが、
`reject-match` は ADR-032 ② により廃止した。敗者が単独で `DRAWN` へ到達できる経路であり、
レート変動なし・記録なしで試合を消せたためである。**番号は再利用しない。**

反論の手段は反対申告（`04_BackendInterface.md` 21.2）に置き換わった。反対申告は `MATCH-003` で
二重提出を弾く以外に専用のコードを持たない。**申告と同じ操作であり、同じ扱いをするためである。**

`MATCH-009` は撤回と投了の混同を防ぐ。自分が申告した勝利に投了するのは撤回であって投了ではない。
**撤回の手段は用意しない。** 用意すると、申告を出しては引っ込めて相手の承認期限を消費できる。

# 13.1 Season

| Code       | HTTP | 内容                     |
| ---------- | ---- | ---------------------- |
| SEASON-001 | 409  | シーズン切替中のため操作できません      |
| SEASON-002 | 409  | マッチングは一時停止中です          |
| SEASON-003 | 409  | シーズンの状態が操作と一致しません      |
| SEASON-005 | 409  | データを持ち出していないため削除できません  |

`SEASON-001` は確定処理の最中に利用者側の更新を止めるものである（Issue #9）。
退避した内容と実データが食い違うのを防ぐ。ログインと閲覧は妨げない。

`SEASON-004` は欠番である。当初「猶予期間が終了していません」を割り当てたが、
`finalize-season` は猶予中に何もせず正常終了する設計とした（12.7）。cron から呼ぶ内部処理であり、
猶予中の呼び出しは異常ではないためエラーを返さない。**番号は再利用しない。**

`SEASON-005` は取り消せない削除の安全弁である。該当シーズンの持ち出し記録
（`season_exports`）が無ければ削除を拒否する。

# 13.2 Abuse Report

通報（ADR-033）に関するコードである。**通報は勝敗フローから独立しているため、`MATCH-*` を用いない。**

| Code      | HTTP | 内容                    |
| --------- | ---- | --------------------- |
| ABUSE-001 | 404  | 通報対象のチームが存在しません       |
| ABUSE-002 | 400  | 自チームは通報できません          |
| ABUSE-003 | 409  | この試合については既に通報しています    |
| ABUSE-004 | 409  | 通報の間隔が短すぎます           |
| ABUSE-005 | 404  | 通報が存在しません             |
| ABUSE-006 | 409  | 通報は既に処理されています         |
| ABUSE-007 | 403  | 通報を取り下げる権限がありません      |

## 使用箇所

| Code      | 発生条件                                                     |
| --------- | -------------------------------------------------------- |
| ABUSE-001 | `targetTeamId` が実在しない                                     |
| ABUSE-002 | `targetTeamId` が通報者の所属チームと一致する                            |
| ABUSE-003 | `matchId` 指定時、同一チームから同一対象・同一試合への通報が既に存在する（取り下げ済みを除く）      |
| ABUSE-004 | `matchId` 未指定時、同一対象への通報が過去24時間以内に存在する                     |
| ABUSE-005 | `withdraw-abuse-report` / `admin-resolve-abuse-report` の対象が存在しない |
| ABUSE-006 | 対象の通報が `OPEN` でない                                        |
| ABUSE-007 | 取り下げの実行者が `reporter_profile_id` と一致しない                    |

`ABUSE-003` と `ABUSE-004` は**通報の濫用を抑えるためのものであり、通報を難しくするためのものではない**。
別の試合について、あるいは24時間後であれば、同じ対象へ何度でも通報できる。

`ABUSE-004` に 429 ではなく 409 を割り当てるのは、本書3章が用いるステータスの範囲に合わせるためである。
通報の頻度制限は業務上の重複判定であり、通信量の制御ではない。

**通報が受理されなかったことを対象チームへ通知しない。** いずれのコードも通報者にのみ返る。

# 14. System

| Code       | HTTP | 内容            |
| ---------- | ---- | ------------- |
| SYSTEM-001 | 500  | 内部エラーが発生しました  |
| SYSTEM-002 | 500  | データベースエラー     |
| SYSTEM-003 | 500  | Realtime通知エラー |
| SYSTEM-004 | 500  | 外部サービスエラー     |

`SYSTEM-003` はRealtime送信の失敗を示す。**Realtime送信の失敗はトランザクションをロールバックしない。** 通知はコミット後に行うため、通知失敗時はログへ記録し、クライアントは次回の取得で最新状態を得る。

# 15. 冪等な操作の扱い

同じ結果をもたらす再送は、エラーではなく成功として応答する。

| 操作                | 再送時の応答                       |
| ----------------- | ---------------------------- |
| admin-ban-team    | 既にBAN済みでも `OK`               |
| admin-unban-team  | 既に解除済みでも `OK`                |
| admin-update-system-settings | 同一値でも `OK`         |
| cancel-match-queue | 既に待機解除済みの場合は `QUEUE-004`     |

一方、状態遷移を伴う操作（報告・承認・拒否）は再送を成功として扱わない。

二重実行を防ぐため、状態と `version` の検証により `MATCH-002` / `MATCH-003` / `MATCH-004` / `MATCH-008` のいずれかを返す。これらを受信したクライアントは、最新状態を再取得して画面を更新する。

# 16. AI実装ルール

* すべてのEdge Functionは `result` を返却する。
* 成功時は `result = "OK"`、業務エラー時は `"NG"`、システムエラー時は `"FATAL"` とする。
* エラー時は必ず `error.code` と `error.message` を返却する。
* `error.message` は英語の短文とし、利用者向けの文言はフロントエンドが `error.code` から生成する。
* フロントエンドは `error.code` を基準に画面表示を切り替える。`error.message` を直接表示しない。
* 本書に定義のないエラーコードを実装してはならない。
* テストコードでは HTTPステータスと `error.code` の両方を検証する。
* 業務ルール違反は409で統一する。422を使用しない。
