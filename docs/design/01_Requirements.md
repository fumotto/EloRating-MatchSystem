# 2. システム概要

本システムは、固定メンバーで構成されるチーム同士が対戦し、その戦績を管理するWebアプリケーションである。

プレイヤーは外部OAuthプロバイダのアカウントでログインし、チームを作成するか、招待を受けてチームへ参加する。

チームはマッチングキューへ参加し、対戦相手が決定すると試合が成立する。

試合終了後は勝利チームが結果を申告し、敗北チームが承認することで試合結果が確定する。

試合結果に応じてEloレーティングを更新し、ランキングへ反映する。

本システムは対戦の管理を行うものであり、ゲーム本体とは連携しない。試合の進行状況や終了をシステムが検知することはできない。

---

# 3. 開発目的

* 固定チーム戦の公平なレート管理
* 戦績管理の自動化
* Discordコミュニティ等で利用できる簡単な運営ツール
* 小規模運営でも管理できるシンプルなシステム
* 将来的な機能追加を前提とした拡張性の高い設計

# 5. 利用者

## プレイヤー

* ログイン
* チーム作成・参加・脱退
* リーダー移譲
* マッチング
* 試合結果の投了・申告・承認・反対申告
* 対戦不成立の申請
* 通報
* ランキング閲覧

## 管理者

プレイヤーの操作に加えて以下を行える。

* チームBAN・BAN解除
* システム設定変更
* レートリセット
* 監査ログ閲覧

管理者はSupabaseプロジェクトの運用者が指定する。Supabase Auth の `app_metadata` にロールを設定することで付与し、**アプリケーションに管理者を登録・昇格させる機能は設けない**（ADR-020）。

## 未認証の閲覧者

ランキングのみ閲覧できる（ADR-018）。

# 6. MVP対象機能

## 6.1 認証

外部OAuthプロバイダによる認証を行う。

対応プロバイダは **Discord** とする（ADR-022）。

プロフィールはプロバイダ非依存の設計を維持する（ADR-015）。Steam 対応は将来機能とする（`13_FutureFeatures.md`）。

| 機能        | 内容                    |
| --------- | --------------------- |
| ログイン      | 外部OAuthプロバイダによる認証     |
| ログアウト     | セッションの破棄              |
| プロフィール取得  | ログイン利用者の情報取得          |
| プロフィール自動作成 | 初回ログイン時にプロフィールを作成する   |

システムは認証プロバイダに依存しない設計とする。

---

## 6.2 チーム管理

プレイヤーはチームを作成するか、招待を受けて参加する。

| 機能       | 内容                     |
| -------- | ---------------------- |
| チーム作成    | 作成者がリーダーとなる            |
| 招待発行     | リーダーが招待コードを発行する        |
| 招待参加     | 招待コードを使用してチームへ参加する     |
| メンバー一覧表示 | 所属メンバーを表示する            |
| 脱退       | チームから脱退する              |
| リーダー移譲   | リーダー権限を他メンバーへ譲渡する      |

### 制約

* 1プレイヤーは1チームのみ所属可能
* チーム人数は管理者設定値以内
* **チームへの参加は招待制のみとする**（ADR-013）
* 1チームにリーダーは必ず1人存在する
* 試合中は脱退できない
* 他メンバーが存在する場合、リーダーは移譲せずに脱退できない
* チーム名の変更およびチーム削除はMVP対象外

---

## 6.3 マッチング

チーム単位でマッチングを行う。

| 機能       | 内容                |
| -------- | ----------------- |
| マッチングキュー参加 | リーダーが待機を開始する      |
| キュー離脱    | 待機を取り消す           |
| マッチ成立通知  | 相手が決定したことを通知する    |

### 制約

* 待機開始はチームリーダーのみ実行できる
* 進行中の試合があるチームはマッチングできない
* BANされたチームはマッチングできない
* レート差が設定値以内のチーム同士をマッチングする
* 相手が見つからない場合は待機を継続する（エラーではない）

---

## 6.4 試合管理

マッチ成立から結果確定までを管理する。

### フロー

```text
1. マッチ成立（この時点で試合は進行中となる）
2. 勝者チームのメンバーが勝利申告
3. 敗者チームのメンバーが承認
4. レート更新
5. ランキング更新
```

システムは試合の開始・終了を検知できないため、「試合開始」という操作は存在しない。マッチ成立と同時に進行中となる（ADR-008）。

### 試合状態

| 状態                | 内容                    |
| ----------------- | --------------------- |
| PLAYING           | マッチ成立から結果申告までの進行中状態   |
| WINNER_REPORTED   | 勝者が申告し、敗者の承認を待つ状態     |
| COMPLETED         | 結果が確定し、レートを更新した状態     |
| DRAWN             | 引き分けまたは時間切れにより解散した状態  |

### 勝敗登録方式

**投了（敗北の自己申告）を基本の経路とする**（ADR-032 ①）。勝者申告 ＋ 敗者承認（ADR-003）は、
敗者が投了しない場合の代替経路として残す。

* **投了は敗者チームのいずれのメンバーでも**実行でき、**承認を要さず即座に確定する**
  自分に不利な申告に虚偽の動機は無いためである
* 勝利申告は**勝者チームのいずれのメンバーでも**実行できる
* 承認は**敗者チームのいずれのメンバーでも**実行できる
* 同一チーム内で複数名が同時に操作した場合は早い者勝ちとする（ADR-009）
* 確定後は結果を変更できない。**訂正の手段を設けない**（ADR-033 ①）

### 設計の前提

**「マッチしたチームは敗北を誤魔化そうとする」を前提に置く**（ADR-032）。

したがって、参加者が単独で「レート変動なし」の終端へ到達できる経路を設けない。
誤魔化す経路の代償は**レートではなく時間**（マッチング待機のクールダウン）で払わせ、
レートは強さの指標として保つ（ADR-004）。

**正直な確定が最も速い。** 投了と承認にはクールダウンが無く、直ちに次の試合へ進める。

### 反対申告

申告された勝敗に異議がある場合、相手チームは**自チームの勝利を申告する**（ADR-032 ⑩）。

「負けていない」という否認は用意しない。無料で検証不能だからである。
「勝ったのは我々だ」は帰属可能で処罰可能な主張であり、記録され公開される。

競合はいずれかの投了で解ける。解けないまま承認期限を過ぎた場合は引き分けとして解散し、
**両チームがクールダウンと不戦を負う。**

### 対戦不成立

回線相性やゲーム側の障害により、当事者に落ち度が無くても対戦が成立しないことがある（ADR-034）。

いずれのチームも不成立を申請でき、**結末は相手の応答で決まる。**

| 相手の応答          | 結末                        |
| -------------- | ------------------------- |
| 承諾             | 引き分け。**双方に代償なし**          |
| 対戦継続・申告・投了・延長  | 試合は継続する                   |
| 無応答            | 引き分け。**無応答側のみ**が代償を負う     |

### 通報

不正・迷惑行為は通報できる（ADR-033）。**通報は勝敗フローから完全に独立している。**

* 対象はチームであり、試合ではない。**いつでも、双方のチームが出せる**
* **通報は勝敗・レート・試合の状態に一切影響しない**
* 措置はマッチング待機のクールダウンと BAN に限る。**確定した結果は覆らない**
* **単発の通報では措置しない。** 異なるチームからの累積を根拠とする

### 自動解決

試合が放置されると、両チームが次の試合に参加できなくなる。これを防ぐため以下を自動的に実施する（ADR-014）。

| 条件              | 動作                    |
| --------------- | --------------------- |
| 申告期限を過ぎても申告がない  | 引き分けとして解散する（レート変動なし）  |
| 承認期限を過ぎても応答がない  | 自動的に承認し、レートを更新する      |

期限は管理者が設定できる（初期値：申告期限60分、承認期限60分）。

承認期限の初期値は ADR-032 ⑨ で 10分 から 60分 へ改めた。承認期限が短いほど、
遅い報告が「相手が見ていない時間帯を狙う」奇襲として機能するためである。

申告期限の起点はマッチ成立時刻である。システムは試合終了を検知できないためである。

## 6.5 レーティング

Elo Rating を採用する。レーティングはチーム単位で管理する。

管理対象の設定値は初期レート・K値とする。

詳細仕様は `08_RatingSpecification.md` で定義する。

---

## 6.6 ランキング

| 表示内容 |
| ---- |
| 順位   |
| チーム名 |
| レート  |
| 勝数   |
| 敗数   |
| 試合数  |
| 勝率   |

BANされたチームはランキングに表示しない。

引き分け（DRAWN）は戦績に計上しない。

ランキングは未認証でも閲覧できる（ADR-018）。プレイヤー個人を特定できる情報は含めない。

---

## 6.7 管理機能

| 機能        | 内容                    |
| --------- | --------------------- |
| チームBAN    | チームを凍結する              |
| BAN解除     | 凍結を解除する               |
| システム設定変更  | 人数上限・K値・各種期限などを変更する   |
| レートリセット   | 全チームのレートを初期値へ戻す       |
| 監査ログ閲覧    | 管理操作・結果確定などの記録を閲覧する   |

レートリセットはシーズン機能ではない。進行中の試合が存在しない場合のみ実行できる。

## 性能

* 同時利用100人程度

GitHub Pages および Supabase のサービス可用性に依存する。目標99%以上。

* OAuth認証
* HTTPS通信
* Row Level Security
* 権限管理
* 監査ログの記録

## 保守性

設計資料を更新しながら開発を行う。設計変更は `15_DecisionLog.md` を起点とする。

## 拡張性

新機能追加時に既存機能へ影響を最小限とする。

# 8. システム制約

* 外部OAuthプロバイダによるログインが必須
* チーム単位でのみ試合を行う
* 個人レートは保持しない。チームレートのみ管理する
* 1チームは同時に1試合まで
* システムはゲーム本体と連携せず、試合の進行を検知できない
* マッチング以外の方法で試合を開始する手段は提供しない
