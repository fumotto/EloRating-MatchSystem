# 1. 目的

本書は「固定チームレート戦 戦績管理システム」の基本設計を定義する。

本設計は、画面・データ・API・状態管理・権限管理の全体構造を示し、実装者およびAIコーディングエージェントが同一の設計思想に基づいて実装できることを目的とする。

本書は**全体構造**の正本である。個々の詳細は各設計書を正本とし、本書へ重複して記載しない。

# 2. システム構成

```text
+----------------------------+
|        GitHub Pages        |
|   React + TypeScript SPA   |
+-------------+--------------+
              |
              | HTTPS
              |
      +-------+--------+---------------+
      |                |               |
      v                v               v
+-----------+   +--------------+  +----------+
| Supabase  |   | Edge         |  | Realtime |
| Auth      |   | Functions    |  |          |
+-----+-----+   +------+-------+  +----+-----+
      |                |               |
      | RLS            | 直接接続        |
      v                v               |
+---------------------------------+    |
```

読み取りは RLS で保護された Query、更新は Edge Functions を経由する。

Edge Functions は PostgreSQL へ直接接続してトランザクションを制御する（ADR-016）。

# 5. 設計方針

## 5.1 単一責務

各機能は一つの責務のみを持つ。チーム管理・マッチング・試合管理・レーティングは互いに独立したモジュールとして設計する。

## 5.2 状態管理

**サーバーデータはデータベースを唯一の正とする。**

画面側はサーバーデータを保持せず、取得したデータを表示する。UI状態（ダイアログの開閉、テーマ等）は画面側で保持してよい。

リアルタイム更新は Supabase Realtime を利用し、通知受信時はデータを再取得する。

## 5.3 導出可能な状態を保持しない

他のデータから導出できる状態を、専用の列として保持しない。

例として、チームが試合中であるかは `matches` から導出する。`teams.status` のような列は設けない（`03_Database.md` 7.3）。

二重管理による不整合を防ぐためである。

## 5.4 権限管理

権限は Row Level Security と Edge Functions 内の認可チェックの二重で制御する。

Edge Functions は PostgreSQL へ直接接続するため RLS を迂回する。したがって Edge Function 内の認可チェックは必須である。

画面側のガードは利便性のためのものであり、認可の保証としない。

# 9. 試合フロー

```text
キュー参加
  ↓
マッチ成立（status = PLAYING）
  ↓
勝利申告（status = WINNER_REPORTED）
  ↓
  ├── 承認 ────→ COMPLETED → レート更新 → ランキング更新
  ├── 反対申告 ──→ 競合。投了で決着、未決着なら DRAWN（CONFLICT）
  └── 承認期限切れ → 自動承認 → COMPLETED → レート更新
                    ★反対申告があるうちは自動承認しない

投了（基本の経路）→ 即 COMPLETED → レート更新

申告期限切れ → DRAWN（REPORT_TIMEOUT / レート変動なし）
不成立の申請 → 承諾なら DRAWN（MUTUAL）、無応答なら DRAWN（NO_SHOW）
```

# 10. 状態遷移

## 10.1 Match

状態遷移の正本は `03_Database.md` 7.1 である。本書は概要のみ示す。

```text
                 ┌──投了（基本の経路）──────────────────→ COMPLETED
PLAYING ──申告──→ WINNER_REPORTED ──承認／自動承認──────→ COMPLETED
   │                    │
   │                    └──反対申告──→ 競合 ──期限切れ──→ DRAWN
   │
   └─申告期限切れ／不成立の申請（承諾・無応答）／管理者の無効化──→ DRAWN
```

`DRAWN` の内訳は `matches.no_contest_reason` で区別する（ADR-034 ①）。
`REPORT_TIMEOUT` / `NO_SHOW` / `CONFLICT` / `MUTUAL` / `ADMIN_VOID` の5種類であり、
**クールダウンの有無と確定率への計上が異なる。一律に扱ってはならない。**

**`WINNER_REPORTED → PLAYING`（拒否）は廃止した**（ADR-032 ③）。

`MATCHED`・`IN_PROGRESS` は使用しない。

## 10.2 Team

チームに状態遷移は存在しない。

BAN状態は `teams.is_banned`、試合中かどうかは `matches` から導出する（5.3）。

# 11. 権限設計

| 操作          | 実行できる利用者              |
| ----------- | --------------------- |
| ランキング閲覧     | 未認証を含むすべての利用者         |
| チーム作成       | 認証済み（未所属）             |
| 招待参加        | 認証済み（未所属）             |
| 脱退          | チームメンバー               |
| 招待発行        | チームリーダー               |
| リーダー移譲      | チームリーダー               |
| キュー参加・離脱    | チームリーダー               |
| **勝利申告**    | **勝者チームのいずれのメンバー**    |
| **投了**      | **敗者チームのいずれのメンバー**    |
| **承認・反対申告** | **相手チームのいずれのメンバー**    |
| 期限の延長・不成立の申請 | いずれかの参加チームのメンバー      |
| 通報          | 認証済みの全利用者（チーム所属を要さない） |
| BAN / 設定変更 / レートリセット / 監査ログ閲覧 | 管理者 |

勝利申告・承認をリーダーに限定しない理由は、リーダー不在時に試合結果が確定できず滞留することを防ぐためである（ADR-009）。

管理者かどうかはJWTの `app_metadata.role` で判定する（ADR-020）。管理者の指定はSupabase側で行い、アプリケーションに登録機能を設けない。

# 12. 通知

Realtime を利用する。イベント名の正本は `04_BackendInterface.md` 7章である。

通知対象は以下の事象とする。

* マッチ成立
* 勝利申告・反対申告
* 報告期限の延長
* 不成立の申請と応答
* 試合完了
* 引き分け解散

**通報は通知しない。** 通報の発生を対象にも他人にも知らせない（ADR-033）。
* ランキング更新
* チーム情報・メンバーの更新
* システム設定の変更

実装方式は Broadcast とし、コミット成功後に送信する。

# 15. ログ

## 15.1 監査ログ

`audit_logs` テーブルへ記録する（ADR-017）。MVPの対象である。

記録対象は以下とする。

* 管理者操作（BAN、設定変更、レートリセット）
* チーム作成
* マッチ成立
* 投了・勝利申告・承認・反対申告・引き分け解散
* 通報の登録・取り下げ・措置
* 認証失敗・権限違反

本テーブルは追記専用とし、参照は管理者のみとする。

## 15.2 実行ログ

Edge Functions は実行内容を標準出力へ記録する（`04_BackendInterface.md` 17章）。監査ログとは別物である。

個人情報・アクセストークン・招待コードの平文を出力しない。

# 16. パフォーマンス

* 一覧画面はページング可能な構造とする
* ランキングはレート降順で取得し、専用Viewを利用する
* Realtime を利用する画面ではポーリングを行わない
