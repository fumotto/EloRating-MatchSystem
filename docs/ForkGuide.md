# 0. はじめに

## 0.1 この文書について

このシステムをコピーして、**自分専用のサイト**として公開するための手順書です。

プログラミングの知識は要りません。画面を見ながら値をコピーして貼り付ける作業が中心です。
コマンドを打つ場面はなく、すべてブラウザ上で完結します。

開発者向けの手順は `docs/project/SetupRunbook.md` にあります。こちらは読まなくて構いません。

## 0.2 完成すると何ができるか

- Discord アカウントでログインできる、自分だけのサイトが公開されます
- 利用者はチームを作り、仲間を招待できます
- 「マッチング」を押すと、実力（レート）の近いチーム同士が自動で対戦相手として組まれます
- 勝敗を申告・承認すると、将棋やチェスと同じ **Elo レーティング** で強さの数値が更新されます
- ランキングはログインしていない人でも見られます

## 0.3 かかる時間とお金

| 項目 | 目安 |
| --- | --- |
| 作業時間 | 60〜90分（初めての場合） |
| 費用 | **無料**（各サービスの無料枠に収まります） |

無料枠には上限があります。利用者が増えて上限に近づくと、各サービスからメールで通知が来ます。

## 0.4 必要なもの

以下の3つのサービスのアカウントを作ります。すべて無料です。

| サービス | 役割 | 例えるなら |
| --- | --- | --- |
| **GitHub** | プログラムの保管庫。サイトの公開も行う | 土地と建物 |
| **Supabase** | データの保管庫。ログインの窓口 | 倉庫と受付 |
| **Discord** | ログインに使う本人確認 | 身分証の発行元 |

Discord のアカウントは既に持っている方が多いと思います。持っていなければ作ってください。

## 0.5 作業の流れ

上から順に進めてください。**順番を入れ替えないでください。** 後の手順で前の手順の値を使うためです。

```text
手順1  GitHub でコピーを作る          → サイトの住所（URL）が決まる
   ↓
手順2  Supabase でプロジェクトを作る   → データの保管場所ができる
   ↓
手順3  Discord アプリを作る            → ログインの仕組みができる
   ↓
手順4  Supabase に Discord を登録      → 手順2と3をつなぐ
   ↓
手順5  Supabase に接続情報を登録       → データベースへの通り道を作る
   ↓
手順6  GitHub に設定値を登録           → 手順2の値を GitHub へ渡す
   ↓
手順7  GitHub Pages を有効にする       → 公開の準備
   ↓
手順8  公開する（デプロイ）             → サイトが動き出す
   ↓
手順9  動作を確認する
   ↓
手順10 自分を管理者にする
   ↓
手順11 定期処理を有効にする（重要）
```

作業中に何度も使う値があります。この表を紙かメモ帳に写して、手に入れるたびに書き込んでください。

**この表には秘密の情報が含まれます。他人に見せたり、SNS に貼ったりしないでください。**

| # | 名前 | 手に入る場所 | 控えた値 |
| --- | --- | --- | --- |
| A | GitHub ユーザー名 | 手順1 | |
| B | サイトの URL | 手順1 | |
| C | Project URL | 手順2 | |
| D | project-ref | 手順2 | |
| E | データベースのパスワード | 手順2 | |
| F | Publishable key | 手順2 | |
| G | Service role key ⚠️ | 手順2 | |
| H | アクセストークン ⚠️ | 手順2 | |
| I | Discord Client ID | 手順3 | |
| J | Discord Client Secret ⚠️ | 手順3 | |
| K | 接続文字列（Session） ⚠️ | 手順5 | |
| L | 接続文字列（Transaction） ⚠️ | 手順5 | |

⚠️ の付いた5つは**特に重要な秘密情報**です。他人に知られると、データを勝手に読み書きされます。

# 1. 手順1：GitHub でコピーを作る

## 1.1 GitHub アカウントを作る

すでに持っている方は 1.2 へ進んでください。

1. <https://github.com/signup> を開きます
2. メールアドレス、パスワード、ユーザー名を入力します
   - **ユーザー名はサイトの URL に入ります。** 後から変えると設定をやり直すことになるので、
     気に入った名前にしてください（半角英数字とハイフン）
3. メールに届いた確認コードを入力します

控えます。

> **A：GitHub ユーザー名** → 例 `taro-yamada`

## 1.2 コピー（fork）を作る

「fork（フォーク）」は、他人のプログラムを自分の場所に丸ごとコピーする操作です。
コピー後は自由に触れます。元のプログラムには影響しません。

1. <https://github.com/fumotto/EloRating-MatchSystem> を開きます
2. 画面右上の **Fork** ボタンを押します
3. 設定画面が出ます。次のようにします

   | 項目 | 設定 |
   | --- | --- |
   | Owner | 自分のユーザー名（そのまま） |
   | Repository name | `EloRating-MatchSystem` のまま**変えない** |
   | Copy the default branch only | チェックを入れたまま |

4. **Create fork** を押します

### ⚠️ 名前を変えたい場合

`Repository name` を変えると、サイトの URL と手順6で登録する値の両方が変わります。
変えること自体は可能ですが、**手順6の `VITE_BASE_PATH` を必ず新しい名前に合わせてください。**
不安であれば、そのままの名前を強く勧めます。

### ⚠️ 公開設定はそのままに

fork したコピーは「Public（公開）」になります。**そのままにしてください。**
「Private（非公開）」にすると、サイトの公開に GitHub の有料プランが必要になります。

公開されるのはプログラムだけです。利用者のデータは Supabase 側にあり、公開されません。

## 1.3 サイトの URL を控える

これがあなたのサイトの住所になります。まだ開いても何も表示されませんが、後で使います。

```text
https://＜A：GitHubユーザー名＞.github.io/EloRating-MatchSystem/
```

**末尾のスラッシュ `/` まで含めてください。**

> **B：サイトの URL** → 例 `https://taro-yamada.github.io/EloRating-MatchSystem/`

## 1.4 自動処理を有効にする

fork したコピーでは、自動処理（Actions）が最初は止まっています。これを動かせるようにします。

1. コピーしたリポジトリの上部にある **Actions** タブを開きます
2. 「Workflows aren't being run on this forked repository」という黄色い案内が出ます
3. **I understand my workflows, go ahead and enable them** という緑のボタンを押します

案内が出ない場合は、すでに有効です。次へ進んでください。

## 1.5 できたことの確認

- [ ] `https://github.com/＜A＞/EloRating-MatchSystem` が開ける
- [ ] Actions タブに「Deploy」と「CI」の名前が見えている

# 2. 手順2：Supabase でプロジェクトを作る

利用者の情報、チーム、試合結果などを保管する場所を用意します。

## 2.1 アカウントを作る

1. <https://supabase.com/dashboard/sign-up> を開きます
2. **Continue with GitHub** を押すと、手順1の GitHub アカウントでそのまま登録できます（おすすめ）
3. GitHub から「Supabase に許可しますか」と聞かれるので **Authorize** を押します

## 2.2 組織（Organization）を作る

初回ログイン時に組織の作成を求められます。個人利用でも1つ必要です。

| 項目 | 設定 |
| --- | --- |
| Name | 好きな名前（例：`taro-personal`） |
| Type | `Personal` |
| Plan | **Free** |

## 2.3 プロジェクトを作る

**New project** を押します。

| 項目 | 設定 | 注意 |
| --- | --- | --- |
| Name | 好きな名前（例：`elorating`） | 後から変更可 |
| Database Password | **強いパスワードを作る** | ★下記参照 |
| Region | `Northeast Asia (Tokyo)` | 日本から使うなら東京 |

### ⚠️ データベースのパスワードについて

**この画面を閉じると二度と表示されません。** 必ず今すぐ控えてください。

`Generate a password` ボタンで自動生成されたものをコピーするのが確実です。
自分で決める場合は、記号 `@ : / ? # [ ] &` を**使わないでください**。
後の手順で URL の一部として扱うため、これらの記号があると正しく動きません。

> **E：データベースのパスワード** → 控える ⚠️

**Create new project** を押します。準備に2〜3分かかります。コーヒーでも淹れてお待ちください。

## 2.4 プロジェクトの情報を控える

準備が終わったら、左メニュー下部の **Project Settings（歯車アイコン）→ Data API** を開きます。

**Project URL** を控えます。

> **C：Project URL** → 例 `https://abcdefghijklmnopqrst.supabase.co`

この URL のうち、`https://` と `.supabase.co` に挟まれた**英小文字20文字**が「project-ref」です。

```text
https://abcdefghijklmnopqrst.supabase.co
        ^^^^^^^^^^^^^^^^^^^^
        ここが project-ref
```

> **D：project-ref** → 例 `abcdefghijklmnopqrst`

## 2.5 API キーを控える

**Project Settings → API Keys** を開きます。2種類のキーがあります。

| 名前 | 性質 | 用途 |
| --- | --- | --- |
| **Publishable key** (`sb_publishable_...`) | 公開してよい | サイトに埋め込む |
| **Secret key** (`sb_secret_...`) | ⚠️ 絶対に公開しない | 手順11で使う |

> **F：Publishable key** → 控える
> **G：Service role key** → 控える ⚠️

### ⚠️ 2つのキーの違いは重大です

**Publishable key** は誰でも見られる前提の鍵です。サイトを開けば誰でも取り出せます。
これで許される操作は制限されているため、公開されても問題ありません。

**Service role key** はすべての制限を無視できる鍵です。**他人に知られると、
全利用者のデータを自由に読み書き・削除されます。** 手順6で「Variable」の欄に
間違って入れると全世界に公開されてしまいます。絶対にしないでください。

## 2.6 アクセストークンを発行する

GitHub が Supabase を操作するための鍵です。プロジェクトの鍵とは別物です。

1. <https://supabase.com/dashboard/account/tokens> を開きます
2. **Generate new token** を押します
3. 名前を入れます（例：`github-actions`）
4. 表示された `sbp_` で始まる文字列を控えます

**この画面を閉じると二度と表示されません。**

> **H：アクセストークン** → 例 `sbp_1234...` ⚠️

### ⚠️ よくある間違い

ここで控えるのは **アカウント設定の Access Tokens** で発行した `sbp_` で始まる値です。
手順2.5 の API キーとは**別物**です。混同すると手順8で
`Invalid access token format` というエラーで止まります。

## 2.7 できたことの確認

- [ ] C〜H の6つの値を控えた
- [ ] G（Service role key）と H（アクセストークン）を他人に見せていない

# 3. 手順3：Discord アプリを作る

利用者が Discord アカウントでログインできるようにします。

## 3.1 アプリを作る

1. <https://discord.com/developers/applications> を開きます（Discord のログインが必要です）
2. 右上の **New Application** を押します
3. 名前を入れます（例：`マイレーティングサイト`）
   - **この名前は利用者のログイン画面に表示されます**
4. 利用規約に同意して **Create** を押します

## 3.2 戻り先を登録する

Discord にログインした後、利用者をどこへ戻すかを登録します。

1. 左メニューの **OAuth2** を開きます
2. **Redirects** の **Add Redirect** を押します
3. 次の文字列を入力します。`＜D＞` は手順2.4 で控えた project-ref に置き換えます

   ```text
   https://＜D：project-ref＞.supabase.co/auth/v1/callback
   ```

   例：`https://abcdefghijklmnopqrst.supabase.co/auth/v1/callback`

4. 画面下の **Save Changes** を押します

### ⚠️ ここを間違えるとログインできません

戻り先は**あなたのサイトの URL ではありません。** Supabase の受付窓口の住所です。

利用者から見ると最後は自分のサイトに戻ってきますが、Discord が直接呼ぶのは
Supabase の窓口だからです。ここに B（サイトの URL）を入れると
`redirect_uri mismatch` というエラーになります。

## 3.3 Client ID と Client Secret を控える

同じ **OAuth2** の画面にあります。

**CLIENT ID** をコピーします。

> **I：Discord Client ID** → 例 `1234567890123456789`

### ⚠️ Client ID は「数字」です

**18〜19桁の数字**です。アプリの名前ではありません。

`マイレーティングサイト` のような名前を控えてしまうと、手順4で登録しても
ログイン時に Discord が「無効なクライアント」というエラーを返します。
数字の列であることを必ず確認してください。

続いて **Reset Secret** を押し、表示された文字列を控えます。

> **J：Discord Client Secret** → 控える ⚠️

**この画面を閉じると二度と表示されません。** 閉じてしまったら、もう一度
**Reset Secret** を押せば新しい値が出ます（古い値は無効になります）。

## 3.4 できたことの確認

- [ ] Redirects に `https://＜D＞.supabase.co/auth/v1/callback` が登録されている
- [ ] I が18〜19桁の数字である
- [ ] J を控えた

# 4. 手順4：Supabase に Discord を登録する

手順2と手順3をつなぎます。

## 4.1 Discord ログインを有効にする

1. Supabase の画面に戻ります
2. 左メニューの **Authentication** →  **Sign In / Providers** を開きます
3. 一覧から **Discord** を探して開きます
4. **Enable Sign in with Discord** をオンにします
5. 次の2つを入力します

   | 欄 | 入れる値 |
   | --- | --- |
   | Client ID | **I**（18〜19桁の数字） |
   | Client Secret | **J** |

6. **Save** を押します

## 4.2 戻り先を許可する

ログイン後に戻ってよい URL を登録します。ここに無い URL へは戻れません。

1. **Authentication** → **URL Configuration** を開きます
2. **Site URL** に **B（サイトの URL）** を入れます

   ```text
   https://＜A＞.github.io/EloRating-MatchSystem/
   ```

3. **Redirect URLs** の **Add URL** を押し、次を追加します

   ```text
   https://＜A＞.github.io/EloRating-MatchSystem/**
   ```

   **末尾の `**`（アスタリスク2つ）を必ず付けてください。** サイト内のどのページへも
   戻れるようにするための書き方です。

4. **Save** を押します

### ⚠️ ここを間違えると、エラーも出ずに変な場所へ飛ばされます

登録が無い URL へ戻ろうとすると、Supabase は**エラーを出さずに** Site URL へ
差し替えます。ログイン自体は成功しているのに、`localhost:3000` のような
まったく関係のない場所へ飛ばされる、という形で現れます。

心当たりがない URL に飛ばされたら、まずこの画面を疑ってください。

### ⚠️ 広すぎる登録をしない

`https://＜A＞.github.io/**` のように**リポジトリ名を省いた形で登録しないでください。**
あなたの GitHub アカウントで公開している**他のサイトすべて**にログイン情報を
渡せてしまいます。必ず `/EloRating-MatchSystem/**` まで含めてください。

## 4.3 できたことの確認

- [ ] Discord が有効になっている
- [ ] Site URL が B と一致している
- [ ] Redirect URLs に `/EloRating-MatchSystem/**` を含む行がある

# 5. 手順5：Supabase に接続情報を登録する

プログラムがデータベースへ接続するための通り道を用意します。

## 5.1 接続文字列を2種類取得する

1. **Project Settings → Database** を開きます
2. **Connection string** の欄を探します
3. タブが並んでいます。**Session pooler** と **Transaction pooler** の
   2つをそれぞれコピーします

どちらも次のような形です。

```text
postgresql://postgres.＜D＞:[YOUR-PASSWORD]@aws-0-ap-northeast-1.pooler.supabase.com:5432/postgres
```

**`[YOUR-PASSWORD]` の部分を E（データベースのパスワード）に置き換えます。**
角カッコ `[ ]` も消してください。

| 種類 | 末尾のポート番号 | 控える先 |
| --- | --- | --- |
| Session pooler | `:5432` | **K** ⚠️ |
| Transaction pooler | `:6543` | **L** ⚠️ |

**違いはポート番号だけ**です。取り違えないよう、番号を確認してから控えてください。

### ⚠️ ホスト名を確認してください

`.pooler.supabase.com` を含んでいることを確認してください。
`db.＜D＞.supabase.co` という形のものは別の接続方法で、後の手順で失敗します。

## 5.2 Edge Function にシークレットを登録する

1. **Project Settings → Edge Functions** を開きます
2. **Secrets** の欄で **Add new secret** を押します
3. 次を入力します

   | 欄 | 入れる値 |
   | --- | --- |
   | Name | `APP_DB_POOL_URL` |
   | Value | **L**（Transaction pooler、`:6543`） |

4. **Save** を押します

### ⚠️ 名前は正確に

`APP_DB_POOL_URL` と一字一句同じにしてください。
`SUPABASE_DB_URL` という名前では登録できません（`SUPABASE_` で始まる名前は
Supabase が予約しているためです）。

## 5.3 できたことの確認

- [ ] K と L を控えた（ポート番号が 5432 と 6543 で違う）
- [ ] `APP_DB_POOL_URL` が登録されている

# 6. 手順6：GitHub に設定値を登録する

ここまでに集めた値を GitHub 側へ渡します。

GitHub には値の入れ場所が2種類あります。**間違えないでください。**

| 種類 | 性質 | ここに入れるもの |
| --- | --- | --- |
| **Variables** | 誰でも見られる | サイトに埋め込まれる値 |
| **Secrets** | 登録後は本人にも見えない | 秘密の値 |

## 6.1 登録画面を開く

1. 自分のリポジトリ（`https://github.com/＜A＞/EloRating-MatchSystem`）を開きます
2. 上部の **Settings** タブを押します
3. 左メニューの **Secrets and variables** → **Actions** を開きます

## 6.2 Variables を3つ登録する

**Variables** タブに切り替え、**New repository variable** を3回押して登録します。

| Name | Value |
| --- | --- |
| `VITE_SUPABASE_URL` | **C**（Project URL） |
| `VITE_SUPABASE_ANON_KEY` | **F**（Publishable key） |
| `VITE_BASE_PATH` | `/EloRating-MatchSystem/` |

### ⚠️ `VITE_BASE_PATH` の書き方

**前後のスラッシュを両方付けてください。** `/EloRating-MatchSystem/` です。

- `EloRating-MatchSystem` ← 誤り（スラッシュ無し）
- `/EloRating-MatchSystem` ← 誤り（末尾のスラッシュ無し）

誤ると、サイトを開いても**真っ白な画面**になります。

手順1.2 でリポジトリ名を変えた方は、その名前に合わせてください。

### ⚠️ ここに秘密の値を入れないでください

`VITE_` で始まる値は、**サイトを開いた人が誰でも読み取れます**。
これは仕組み上どうにもなりません。**G（Service role key）を
ここに入れると全世界に公開されます。** 絶対に入れないでください。

## 6.3 Secrets を4つ登録する

**Secrets** タブに切り替え、**New repository secret** を4回押して登録します。

| Name | Value |
| --- | --- |
| `SUPABASE_ACCESS_TOKEN` | **H**（`sbp_` で始まる） |
| `SUPABASE_PROJECT_REF` | **D**（英小文字20文字） |
| `SUPABASE_DB_PASSWORD` | **E** |
| `SUPABASE_DB_URL` | **K**（Session pooler、`:5432`） |

### ⚠️ よくある間違い

| 欄 | 入れるべきもの | 間違えやすいもの |
| --- | --- | --- |

# 11. 手順11：定期処理を有効にする（重要）

## 11.1 なぜ必要か

このシステムには、決まった時間ごとに自動で動く処理があります。

| 処理 | 内容 |
| --- | --- |
| マッチング | 待機中のチーム同士を組み合わせる |
| 期限切れの処理 | 申告や承認が期限を過ぎた試合を自動で決着させる |
| お掃除 | 期限切れの招待や古い待機を消す |

### ⚠️ この手順を飛ばすと、静かに壊れます

未設定でもエラーは出ません。しかし**期限切れの試合が永久に終わらなくなり**、
そのチームは以後まったくマッチングできなくなります。

エラーが出ないため気付きにくく、利用者から「対戦できない」と言われて
初めて分かる、という形になります。**必ず設定してください。**

## 11.2 設定する

1. Supabase の **SQL Editor** を開きます
2. 次を貼り付けます。2か所を自分の値に置き換えます

   ```sql
   SELECT vault.create_secret(
     'https://＜D：project-ref＞.supabase.co/functions/v1',
     'edge_function_base_url'
   );
   SELECT vault.create_secret('＜G：Secret key＞', 'service_role_key');
   ```

3. **Run** を押します

### ⚠️ 鍵は `sb_secret_` で始まる方です

手順2.5 で控えた **Secret key**（`sb_secret_...`）を使います。
同じ画面の **Legacy API keys** にある `service_role`（`eyJhbG...` で始まる長い文字列）
**ではありません。**

見分けがつかない場合は、実際に試すのが確実です。`200` が返る方が正解です。

```bash
curl -s -X POST https://＜D＞.supabase.co/functions/v1/matchmaker \
  -H "Authorization: Bearer ＜試す鍵＞" -w " [%{http_code}]\n"
```

## 11.3 動いているか確認する

### ⚠️ 「成功」の表示を信用しないでください

次の SQL は Cron の実行結果を出しますが、**これは当てになりません。**

```sql
SELECT jobname, status, start_time
  FROM cron.job_run_details
 ORDER BY start_time DESC
 LIMIT 10;
```

`status` が `succeeded` でも、実際には何も処理されていないことがあります。
この表示が示すのは「SQL を実行できたこと」だけで、その先で
**鍵が違って拒否されていても `succeeded` になります。**

### 正しい確認方法

通信の結果そのものを見ます。設定から2分ほど待ってから実行してください。

```sql
SELECT status_code, left(content, 120) AS body, created
  FROM net._http_response
 ORDER BY created DESC
 LIMIT 5;
```

| 表示される番号 | 意味 |
| --- | --- |
| **`200`** | **成功。これが出れば完了です** |
| `403` | 鍵が違います。上の curl で正しい鍵を確かめてください |
| `401` | 鍵が空か、形式が違います |
| 何も出ない | まだ登録できていません。手順11.2 をやり直してください |

## 11.4 できたことの確認

- [ ] `cron.job_run_details` に `succeeded` の行がある

# 12. 管理者の仕事

管理者としてログインすると、ヘッダーに **管理** が現れます。押すと3つの入口が並びます。

| 入口 | できること |
| --- | --- |
| **チーム管理** | 迷惑なチームのBANと解除 |
| **システム設定** | 人数・期限・レートの調整 |
| **監査ログ** | 誰が何をしたかの履歴 |

管理者になる手順は手順10を参照してください。

## 12.1 管理者を増やす

運営を複数人で行う場合、他の人も管理者にできます。

**その人が一度ログインしてから**、Supabase の **SQL Editor** で実行します。

```sql
UPDATE auth.users
   SET raw_app_meta_data = raw_app_meta_data || '{"role":"admin"}'::jsonb
 WHERE email = '＜管理者にする人のメールアドレス＞';
```

対象者は**一度ログアウトして再ログイン**すると反映されます。

### 管理者を解除する

```sql
UPDATE auth.users
   SET raw_app_meta_data = raw_app_meta_data - 'role'
 WHERE email = '＜解除する人のメールアドレス＞';
```

### ⚠️ 解除は即座には効きません

権限はログイン時に発行される証明書に書き込まれます。**解除しても、その人が
ログアウトするまでは管理者として振る舞えます**（最大1時間）。

急いで止める必要がある場合は、Supabase の **Authentication → Users** から
対象者のセッションを失効させてください。

## 12.2 チームをBANする

不正や迷惑行為があったチームを、対戦に参加できない状態にします。

1. **管理 → チーム管理** を開きます
2. 上部の **BANの理由** を入力します（1〜500文字・必須）
3. 対象チームの **BAN** を押します

### BANすると何が起きるか

| 対象 | 影響 |
| --- | --- |
| マッチング | 新しく待機に入れなくなります |
| 待機中だった場合 | **その場で待機列から外れます** |
| 進行中の試合 | **そのまま続きます。**申告・承認は可能です |
| ランキング | 引き続き表示されます |
| メンバー | チームからは追い出されません |

**BANはチームに対する措置**であり、個人アカウントの停止ではありません。
メンバーはチームを脱退すれば、別のチームで活動できます。

### 解除する

同じ画面の **解除** を押します。理由の入力は不要です。

### ⚠️ 理由は必ず記録されます

入力した理由は監査ログに残ります。**後から編集も削除もできません。**
感情的な文言を書かず、事実を簡潔に記録してください。

第三者が見て判断できる書き方が望ましいです。

- 良い例：`2026-08-15 の対戦で虚偽申告。相手チームからの申告により確認`
- 悪い例：`迷惑`

### BAN と解除は何度でも押せます

既にBANされているチームをもう一度BANしても、エラーにはなりません。
解除も同様です。**押しすぎて壊れることはありません。**

## 12.3 監査ログを見る

**管理 → 監査ログ** を開きます。実行された操作が新しい順に並びます。

### 記録される操作

| 表示 | 意味 |
| --- | --- |
| `TEAM_CREATED` | チームが作られた |
| `TEAM_BANNED` | チームがBANされた |
| `TEAM_UNBANNED` | BANが解除された |
| `MATCH_CREATED` | 試合が組まれた |
| `MATCH_REPORTED` | 勝利が申告された |
| `MATCH_CONCEDED` | 投了で確定した |
| `MATCH_COUNTER_CLAIMED` | 反対申告が出された |
| `MATCH_EXTENDED` | 申告期限が延長された |
| `MATCH_NO_CONTEST_REQUESTED` | 対戦不成立が申請された |
| `MATCH_NO_CONTEST_ACCEPTED` | 不成立に同意した |
| `MATCH_NO_CONTEST_DECLINED` | 対戦継続が選ばれた |
| `MATCH_VOIDED` | 運営が試合を無効にした |
| `MATCH_DRAWN` | 引き分けで解散した |
| `ABUSE_REPORTED` | 通報が出された |
| `ABUSE_WITHDRAWN` | 通報が取り下げられた |
| `ABUSE_RESOLVED` | 通報に措置がとられた |
| `SETTINGS_UPDATED` | システム設定が変更された |
| `SEASON_END_STARTED` | シーズン終了が始まった（マッチング停止） |
| `SEASON_END_CANCELLED` | シーズン終了が取りやめられた |
| `SEASON_FINALIZED` | シーズンが確定した（退避・レート初期化） |
| `SEASON_DATA_PURGED` | 戦績・ログが削除された |
| `SEASON_RESUMED` | 通常営業に戻った |

### 「実行者」の見方

各行の下に「実行者」が表示されます。

- **利用者のID**が入っている → その人が操作した
- **「システム」**と表示される → 定期処理が自動で行った

期限切れによる引き分けや自動承認は「システム」になります。
人が操作したのか自動処理なのかを、ここで見分けられます。

### ⚠️ 記録は消せません

監査ログは**追記だけ**の仕組みです。画面からも SQL からも編集・削除する
手段を用意していません。誤ってBANした場合も、BANした記録と解除した記録の
両方が残ります。

これは意図的な設計です。運営の判断を後から検証できるようにするためです。

## 12.4 異常の通知を受け取る（推奨）

放っておくと、**自動処理が止まっても誰も気付けません。** エラーが表示されないためです。
Discord へ通知が届くようにしておくと、利用者から苦情が来る前に対処できます。

### 手順1：Discord で受け取り口を作る

1. 通知を受け取りたい Discord サーバーを開きます
2. **サーバー設定 → 連携サービス → ウェブフック → 新しいウェブフック**
3. 名前（例：`EloRating 監視`）と投稿先チャンネルを選びます
4. **ウェブフックURLをコピー** を押します

管理者だけが見えるチャンネルを作って、そこへ投稿させるのがよいです。

### 手順2：GitHub へ登録する

リポジトリの **Settings → Secrets and variables → Actions → Secrets** で登録します。

| Name | Value |
| --- | --- |
| `DISCORD_WEBHOOK_URL` | 手順1でコピーしたURL |

### 手順3：通知が届くか確かめる

1. **Actions** タブ → 左から **Monitor** を選びます
2. **Run workflow** を押し、そのまま **Run workflow** を実行します
3. 1分ほどで Discord にメッセージが届きます

**届かなければ、URLを登録し直してください。** ここで確認しておかないと、
本当に異常が起きたときに通知が来ないことに気付けません。

### 何が届くか

異常があったとき：

```text
⚠️ EloRating: 異常を検知しました

・期限切れの試合が 3 件残っています（自動解決が止まっている可能性）
```

毎週月曜の朝（正常なとき）：

```text
✅ EloRating: 今週も正常です（週次のお知らせ）

・期限切れの試合：なし
・チーム数：9
・直近7日の試合：確定 3 件 / 引き分け 1 件
```

### ⚠️ 毎週の連絡が来なくなったら、それが異常です

正常なときにも週1回お知らせが届くのは、**通知の仕組み自体が壊れていないことを
確かめるため**です。「異常のときだけ知らせる」形にすると、通知が壊れたときに
静かなまま気付けません。

**月曜に連絡が来なかった週は、Actions タブを確認してください。**

なお GitHub は、リポジトリに60日間まったく変更が無いと自動処理を止めます。
その場合も連絡が来なくなるので、同じように気付けます。

## 12.5 トラブルへの対処

利用者から相談を受けたときの調べ方です。

| 相談内容 | 見るところ |
| --- | --- |
| 対戦相手が見つからない | 待機中のチームが他にいるか。許容レート差が狭すぎないか |
| 試合が終わらない | **手順11の定期処理が動いているか**（最初に疑う） |
| 勝ったのにレートが増えない | 監査ログに `MATCH_REPORTED` はあるか。相手が承認していない可能性 |
| 身に覚えのない引き分け | 監査ログの `MATCH_DRAWN` を確認。実行者が「システム」なら期限切れ |
| 対戦できなくなった | そのチームがBANされていないか |

### 定期処理が止まっていないかの確認

**最も多い原因です。** Supabase の SQL Editor で実行します。

```sql
SELECT jobname, status, start_time
  FROM cron.job_run_details
 ORDER BY start_time DESC
 LIMIT 20;
```

`status` が `failed` ばかり、または最近の行が無い場合は止まっています。
手順11の Vault 登録を確認してください。

### 特定のチームの状態を調べる

```sql
SELECT name, rating, is_banned FROM teams WHERE name = '＜チーム名＞';
```

### 止まったままの試合を探す

```sql
SELECT id, status, report_deadline_at, approve_deadline_at
  FROM matches
 WHERE status IN ('PLAYING', 'WINNER_REPORTED')
 ORDER BY created_at;
```

期限を過ぎているのに残っている行があれば、定期処理が動いていません。

## 12.6 システム設定を変える

**管理 → 設定** を開きます。

### 変えられる項目

| 項目 | 初期値 | 意味 |
| --- | --- | --- |
| チーム人数の上限 | 3 | 1チームの人数。**マッチングに必要な人数でもある** |
| 初期レート | 1500 | 新しいチームの持ち点 |

| 承認期限 | 60 | 相手の申告を承認するまでの分数 |

| ランキング掲載の最低対戦相手数 | 3 | これだけ異なる相手と対戦するまで一覧に載せない。**0 で無効**（12.10） |
| シーズン終了の猶予 | 10 | シーズン終了時に進行中の試合を待つ分数 |
| 保守による停止 | オフ | ゲーム側の障害時にマッチングを止める |

**「拒否の上限回数」は無くなりました。** 拒否そのものを廃止したためです（12.8）。
画面にも出しません。効かない設定を並べておくと、調整すれば何か変わると誤解されるためです。

**「保守による停止」だけは数値ではなくボタンです。** 現在が「停止中」か「稼働中」かが表示され、
押すと切り替わります。ゲーム側の障害時は、**これを先に立ててから**進行中の試合を無効化してください
（12.9）。逆順にすると、無効化した直後に新しい試合が成立します。

**シーズンの切替に関する状態はこの画面にありません。** マッチングの停止・利用者操作の停止・
現在のシーズン番号は、シーズンの操作（12.12）だけが書き換えます。ここから触れてしまうと、
シーズン切替の途中で状態を壊せるためです。

変えたい項目にだけ数値を入れて **保存** を押します。空欄の項目は変わりません。

**変更は即座に全利用者へ反映されます。** 進行中の試合の期限は、その試合が
作られた時点の設定で計算済みのため変わりません。次の試合から新しい値になります。

### 変更するときの注意

#### チーム人数の上限

**この値がそのままマッチングに必要な人数になります。** 3 にすると、
3人揃わないチームはマッチングを開始できません。

2人対戦にしたい場合は `2` に変えてください。
人数が揃っていないチームには、マッチング画面で
「チーム人数が足りません」と表示され、開始ボタンが押せない状態になります。

**`1` にすると個人戦になります。** 1人でチームを作り、そのまま対戦できます。
このとき招待コードは発行できません（1人で既に定員に達しているためです）。

#### K値

大きくすると1試合での点数の動きが激しくなります。
参加者が少なく早く序列を付けたい場合は大きめ（40〜48）、
安定させたい場合は小さめ（16〜24）にします。

#### 許容レート差

小さくすると実力の近い相手としか当たらなくなりますが、
**相手が見つかりにくくなります。** 参加チームが少ないうちは
大きめ（600〜800）にしておくとマッチングが成立しやすくなります。

#### 申告期限・承認期限

短くすると、放置された試合が早く決着します。
ただし短すぎると、対戦後に席を外した人が申告する前に期限が来てしまいます。

## 12.7 勝敗の記録がどう守られているか

**「負けを誤魔化そうとする人がいる」という前提で作られています。** 運営として押さえておく点をまとめます。

### 参加者が単独で「無かったこと」にはできない

以前は「拒否」を2回押すと試合が消え、レートが動きませんでした。**これは廃止しました。**

現在、レートが動かない終わり方（引き分け）へ参加者が単独で到達する経路はありません。

| 引き分けの理由 | 到達条件 | 待機（クールダウン） |
| --- | --- | --- |
| 期限切れ | 双方が何もしない | 両チーム |
| 無応答 | 不成立の申請に相手が応答しない | 応答しなかった側だけ |
| 主張の食い違い | 双方が勝利を主張したまま期限切れ | 両チーム |
| 合意による不成立 | **相手の同意が必要** | なし |
| 運営による無効化 | **管理者の操作が必要** | なし |

### 罰はレートではなく時間

**レートは強さの指標のままにしてあります。** 誤魔化す経路を通ると、点が減るのではなく
**次の試合に行くのが遅くなります。**

裏返すと、**投了と承認が最速の道**です。これが「正直が得」の中身です。

### 結果は訂正できません

**確定した試合の勝敗とレートは、管理者でも変更できません。** 訂正の機能はありません。

本システムはゲームに接続しておらず、どちらが勝ったかを検証できないためです。
検証できない以上、訂正の判断も同じ精度でしかできません。

誤りは確定の**前**に解きます。勝利申告の押し間違いは、相手が申告し直して誤った側が投了すれば直せます。
**投了の押し間違いだけは直せません。** 画面には必ず確認ダイアログが出ます。

## 12.8 通報にどう対応するか

**管理 → 通報** を開きます。

### 1件では動かないでください

**単発の通報で措置しないのが原則です。** 1件の告発は雑音であり、
**違うチームからの通報が積み重なったとき**に初めて信号になります。

画面には対象チームごとに「通報元チーム数」と「通報件数」が並びます。
**先に出ている「通報元チーム数」を見てください。** 件数は1チームから何度でも増やせるため、
それだけでは判断材料になりません。

### できる措置

| 措置 | 内容 |
| --- | --- |
| 措置なし | 確認したが何もしない |
| 警告 | 記録のみ。**伝達は Discord で行ってください**（システムに通知機能はありません） |
| クールダウン | 一定時間マッチングできなくする |
| BAN | チームを排除する |

**試合結果を訂正する選択肢はありません。** それが通報の設計です。

### 証拠は期待しないでください

**証拠の添付は任意です。** 録画を必須にすると、記録を残していない正当な訴えが出せなくなり、
累積による判断の材料も集まりません。

証拠が無い通報も受け付けます。だからこそ**累積で判断します。**

### 示し合わせた通報に注意

違うチームからの通報が積み重なっても、**示し合わせている可能性**はあります。
システムはこれを見分けません。通報元の関係性は運営が見て判断してください。

**根拠のない通報を繰り返すチームも措置の対象です。** 通報者側にも記録が残ります。

### 通報は非公開です

通報の件数や内容はランキングにもチーム情報にも出ません。通報された本人にも見えません。
**誰でも無償で出せるため、公開すると通報を浴びせるだけで評判を落とせてしまいます。**

## 12.9 ゲーム側が止まったとき

ゲームの障害やメンテナンスで対戦できなくなったときの手順です。

```text
1. 管理 → 設定 で「保守による停止」をオンにする
2. 管理 → 設定 でお知らせを掲示する
3. 管理 → 試合 で進行中の試合を一括無効化する
4. 復旧したら「保守による停止」をオフにする
```

**★手順1を必ず先に行ってください。** 逆にすると、無効化した直後に新しい試合が組まれます。

### 一括無効化の対象

**既定では「進行中」の試合だけ**が対象です。「承認待ち」を含めるかは選べます。
障害の前に成立していた申告を巻き込んで消さないための既定値です。

### 無効にした試合の扱い

レートは動きません。勝率にも確定率にも計上されません。**両チームともクールダウンはつきません。**
運営都合・外部要因の不成立で、参加者に不利益を与えないためです。

### シーズンの停止とは別です

「保守による停止」と、シーズン終了に伴うマッチング停止は**別の設定**です。
兼用していないのは、**シーズンを再開すると保守停止まで解除されてしまう**からです。

### シーズンの切り替えと重なったとき

**シーズンリセットの最中でも、上の4手順はそのまま実行できます。** 設定の変更・お知らせの掲示・
試合の一括無効化は、いずれもシーズンの切り替えに止められません。止まるのは選手側の操作だけです。

重なったときに気をつけることが3つあります。

**① 猶予中に対戦できなくなったら、試合を無効化してください。**
シーズン終了の猶予は、進行中の試合が終わるのを待つ時間です。障害で対戦できないまま放置すると、
申告期限切れで解散し、**両チームにクールダウンと不戦が付きます。** 当事者に落ち度はありません。
一括無効化ならレートも記録も動きません。

**② 猶予が切れた時点で残っていた試合は、自動で打ち切られます。**
「シーズンの終了により打ち切られました」と表示され、**不利益はありません。**
待たせたくないなら①で先に無効化してください。

**③「通常営業に戻す」を押しても、保守停止は解除されません。**
これは意図した動作です。ゲーム側が直っていないのにマッチングが動き出さないようにしています。
シーズン画面には「マッチング：停止中（保守）」と表示され、押す前にも注意が出ます。
**復旧したら、システム設定で保守停止を別に解除してください。**

## 12.10 サブアカウント対策

同じ人が複数のアカウントを作り、身代わりのチームと対戦して**わざと負けてレートを稼ぐ**ことへの
対策です。**管理 → システム設定** から調整します。

| 設定                     | 初期値  | 無効にする値 | 効果                             |
| ---------------------- | ---- | ------ | ------------------------------ |
| 同じ相手と再戦できない長さ（時間）      | 24   | 0      | 一度対戦したペアを、その間マッチさせません          |
| ランキング掲載の最低対戦相手数        | 3    | 0      | 異なる相手と対戦するまで、ランキングに載せません       |

### なぜ IP アドレスを見ないのか

同一の IP アドレスからの接続はサブアカウントとして疑わしく見えますが、**採用していません。**

* VPN や、パソコンと携帯回線の使い分けで**簡単に回避できます**
* 一方で、**家族・同居人・学校・LAN 会場・携帯電話会社の回線**では、
  まったく無関係な人どうしが同じ IP アドレスになります

回避されやすく、しかも無実の人を巻き込む指標です。代わりに採ったのが上の2つで、
どちらも**対戦の記録だけを見ています。誰が誰なのかを当てにいきません。**
だから VPN でも回線の使い分けでも効き目が変わりません。

### 疑わしい組み合わせを見る

**管理 → 対戦の偏り** の画面に、繰り返し当たっている組み合わせが並びます。

| 見るところ  | 意味                                     |
| ------ | -------------------------------------- |
| 一方向性   | 100% は、一度も逆向きの結果が出ていないという意味です          |
| 同時在席   | **重なり無し** は、2つのチームが同じ時刻に別々の試合へ出たことが一度も無いという意味です |
| 集中     | 稼いだレートのうち、ひとりの相手から得た割合です               |

**「同時在席が重なり無し」が最も重要です。** 人はふたつのチームを同時に操作できません。
IP アドレスを変えても、回線を分けても、この痕跡は消せません。

**★ただし、これは疑いであって証拠ではありません。** 仲の良い常連どうしも同じ形になります。
参加者が少ないうちは特にそうです。画面には措置のボタンを置いていません。
BAN やクールダウンは、通報の画面とチーム管理から、他の材料と突き合わせて判断してください。

### 検証のときは切ってください

自分で複数のアカウントを作って動作を確認したいときは、**両方の設定を 0 にしてください。**
確認が終わったら戻すのを忘れないでください。

### 参加者が少ないうちは

「同じ相手と再戦できない長さ」が長すぎると、相手が見つからなくなります。
参加チームが少ないうちは短くするか、0 にしてください。

**待機している側にエラーは出ません。** 相手が見つからないまま待ち続けるだけなので、
「マッチングが壊れた」と誤解されないよう、設定を変えたときは告知してください。

## 12.11 対戦カードを用意する

大会やイベントで、対戦する2チームを運営が直接指定できます。**管理 → 対戦カードを用意する** です。

### 自動マッチングとの違い

| | 自動マッチング | 対戦カードを用意する |
| --- | --- | --- |
| 相手の決まり方 | レートの近さで自動 | **運営が指定** |
| レート差の上限 | あり（初期400） | **無し** |
| 同じ相手との再戦 | 抑止される（12.10） | **抑止されない** |
| 回線相性による除外 | される | **されない** |
| クールダウン中のチーム | 組まれない | **組める** |
| 進行中の試合があるチーム | 組まれない | **重ねて組める** |

**用意した試合の終わり方は普通の試合と同じです。** 投了・勝利申告・不成立の申請、
どれも同じように使えます。レートも普通に動きます。

### 用意できないとき

| 表示 | 理由 |
| --- | --- |
| BANされたチームです | BAN中は対戦できません |
| メンバーが居ないチームは対戦できません | 誰も結果を報告できず、相手を待たせ続けることになります |
| シーズンの切り替え中のため、操作できません | 用意しても確定処理で打ち切られます |
| マッチングは一時停止中です | 猶予中に増やすと、猶予がいつまでも終わりません |
| メンテナンス中のため、いまは試合を開始できません | ゲーム側が止まっています（12.9） |

### 人数が揃っていなくても組めます

**人数の違うチーム同士でも用意できます。** 自動マッチングと違い、ここでは止めません。
画面に「人数が揃っていません」と出るので、承知のうえで組むか判断してください。

大会では欠員のまま消化することがあるためです。**レートは普通に動きます。**
2人チームが3人チームに勝てば、その分だけレートが移ります。

### 取り消せません

**用意した試合を消すボタンはありません。** 誤って組んだ場合は、

* 当事者どうしで「この試合は不成立」に合意してもらう
* **管理 → 試合** から一括無効化する（12.9）

のどちらかで終わらせてください。作成前に確認画面が出ます。

### 同じ組み合わせを何度でも

**同じ2チームを繰り返し用意できます。** 3本勝負のような運用を想定しています。
1本目が終わってから2本目を用意しても、同時に3本用意しても構いません。

## 12.12 シーズンを切り替える

**管理 → シーズン** の画面で行います。区切りをつけて、レートを初期値に戻す操作です。

1回押して終わりではありません。順番に進みます。

### ① シーズンを終了する

**シーズンを終了する** を押すと、新しいマッチングの受付が止まります。
**進行中の試合はそのまま続けられます。** 対戦相手を巻き添えにしないためです。

このとき、チームを解散するかどうかも選べます。

| 選択 | 意味 |
| --- | --- |
| 通常のチームをすべて解散する | BANされていないチームを削除します |
| BAN中のチームをすべて解散する | BAN中のチームを削除します |

どちらも選ばなければ、チームはそのまま残り、レートだけが戻ります。
**選ぶのはこの時点だけです。** あとの工程は自動で進むため、後から選び直せません。

### ② 待つ（既定10分）

進行中の試合が決着するのを待ちます。**この画面を開いたままにする必要はありません。**

気が変わったら **終了を取りやめる** を押せます。マッチングが再開します。
ただし待っていた人の順番は戻らないので、押し直してもらう必要があります。

猶予が過ぎると、残っている試合は打ち切られて確定処理が自動で始まります。
このとき利用者はチームの操作ができなくなります。

打ち切られた試合は「シーズンの終了により打ち切られました」と表示されます。
**レートは動かず、待機（クールダウン）も付きません。** 打ち切ったのは運営側であり、
選手に落ち度が無いためです。

### ③ データを保存する

確定後、**戦績データを保存** と **ログデータを保存** が押せるようになります。
CSVファイルがダウンロードされます。表計算ソフトで開けます。

**誰が何をしたかの情報は含まれません。** チーム名と試合の結果だけです。

### ④ データを削除する（任意）

**戦績とログを削除する** を押すと、過去の試合記録が消えます。
①でチームの解散を選んでいた場合、ここで一緒に削除されます。

**元に戻せません。** ③で両方を保存していないと押せない仕組みにしてあります。

消さなくても構いません。次のシーズンは問題なく始められます。

### ⑤ 通常営業に戻す

**通常営業に戻す** を押すと、利用者の操作とマッチングが再開します。
**これを押すまで利用者は何もできません。** 忘れないでください。

**「保守による停止」が入っていると、これを押してもマッチングは動きません**（12.9）。
意図した動作です。押す前に画面が注意します。復旧しているなら、
**管理 → 設定** で保守停止も解除してください。

### 過去のシーズンを見る

確定したシーズンは、画面上部の **過去のシーズン** から誰でも見られます。
そのときの順位・レート・勝敗が残ります。チーム名を選ぶと当時のメンバーも確認できます
（メンバーの表示にはログインが必要です）。

**チームを解散しても、過去のランキングは残ります。**

# 13. 日々の運用

## 13.1 プログラムを最新にする

元のプログラムが更新されたとき、自分のコピーにも取り込めます。

1. 自分のリポジトリを開きます
2. **Sync fork** ボタンを押します
3. **Update branch** を押します
4. 手順8のデプロイを実行します

**取り込む前に、何が変わるか分からない場合は急いで更新しないでください。**
今のまま動いているなら、それで問題ありません。

## 13.2 画面の変更だけを反映する

見た目だけを直した場合は、デプロイを速く終わらせられます。

手順8.1 の入力欄で **「バックエンドの適用を飛ばす」** にチェックを入れてください。
データベースの処理を飛ばすため、5分ほどで終わります。

## 13.3 動かなくなったとき

| 症状 | 最初に見る場所 |
| --- | --- |
| サイトが真っ白 | 手順7の Source、手順6.2 の `VITE_BASE_PATH` |
| ログインできない | 手順4.1 の Client ID が数字か |
| ログイン後に変な URL へ飛ぶ | 手順4.2 の Site URL / Redirect URLs |
| 「内部エラー」と出る | 手順5.2 の `APP_DB_POOL_URL` |
| チームは作れるが対戦が始まらない | 手順11の定期処理 |
| 試合が終わらない | 同上 |

## 13.4 データのバックアップ

Supabase の **Database → Backups** から取得できます。
無料枠では日次バックアップが7日分保持されます。

**大事なデータを扱う場合は、有料プランへの変更を検討してください。**

| Pooler | データベースへの接続をまとめて効率よく扱う仕組み |
| Edge Function | Supabase 上で動く小さなプログラム |
| Vault | Supabase の中で秘密の値を安全に保管する場所 |
| Cron | 決まった時刻に自動で処理を動かす仕組み |
| Elo レーティング | 対戦結果から強さを数値化する計算方法。チェスで使われる |

# 15. 困ったときは

## 15.1 設定を確認する

登録した値が正しいか、Supabase の画面で確認できます。

- Discord の設定 → **Authentication → Sign In / Providers → Discord**
- 戻り先の設定 → **Authentication → URL Configuration**
- Edge Function のシークレット → **Project Settings → Edge Functions**

GitHub 側は **Settings → Secrets and variables → Actions** で確認します。
**Secrets に登録した値は表示されません。** 疑わしい場合は、正しい値で
上書き登録してください。

## 15.2 やり直す

設定を間違えても、値を直して手順8のデプロイをやり直せば直ります。
**何度実行しても問題ありません。** データが消えることもありません。

## 15.3 最初からやり直す

どうしても直らない場合は、Supabase のプロジェクトを削除して手順2から
やり直すのが確実です。**利用者のデータもすべて消えます**ので、
公開前であることを確認してください。
