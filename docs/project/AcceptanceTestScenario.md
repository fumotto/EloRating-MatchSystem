# AcceptanceTestScenario.md

# 受入テストシナリオ（人手による挙動確認）

Version: 1.0
Status: Active
Last Updated: 2026-09-03
準拠ADR: ADR-032, ADR-033, ADR-034, ADR-035, ADR-036, ADR-037, ADR-038, ADR-039

---

# 1. 目的

検証環境へ協力者を招き、**実際の人間が操作したときに仕様どおり動くか**を確認する。

自動テスト（`10_TestSpecification.md` Part1〜Part10）は実装が仕様を満たすことを検証する。
本書はそれとは別に、**仕様そのものが人間に対して機能するか**を確認する。

| 本書で見るもの | 自動テストで見るもの |
| --- | --- |
| 説明されなくても操作できるか | 関数が仕様どおりの値を返すか |
| 画面の文言で状況が分かるか | DBが仕様どおり更新されるか |
| 複数人が同時に触ったときに破綻しないか | 認可が仕様どおり働くか |
| 待たされる時間が納得できるか | エラーコードが仕様どおりか |

---

# 2. 本書の位置づけ

**本書は仕様の正本ではない。** 期限・回数・レート計算などの値は `03_Database.md` 17章と
`08_RatingSpecification.md` が正本である。本書の期待結果と設計書が食い違う場合は、
Project Constitution 第9条の優先順位に従い設計書を正とし、**本書を修正する。**

**本書はテストIDの正本でもない。** `10_TestSpecification.md` のテストID（`TC-` 接頭辞）は
自動テストの正本であり、本書は別系統の `UAT-` 接頭辞を用いる。両者を対応付けない。
人手でしか確認できないことを人手で確認するのが本書の役割であり、
自動テストの再実行ではないためである。

# 3. 適用範囲

## 3.1 対象

MVP の全機能。選手の操作、管理者の操作、未認証の閲覧。

## 3.2 対象外

| 項目 | 理由 |
| --- | --- |
| 性能・負荷 | 100人・30試合の同時利用は協力者の人数で再現できない |
| Discord OAuth の内部挙動 | 外部サービスであり、本システムの検証範囲ではない |
| 定期処理の障害復旧 | `monitoring_guide.md` の範囲 |
| ブラウザ互換性の網羅 | 5.2 で代表的な組み合わせのみ確認する |

## 3.3 実施しない操作

**検証環境であっても、次の操作は本シナリオに含めない。**

* 本番の Supabase プロジェクトに対する操作
* `admin-purge-season-data`（データ削除）を検証環境の記録を残したまま実行すること
  — 9章の後片付けで、意図して実行する場合のみ行う

# 4. 実施体制

## 4.1 役割

| 役割 | 人数 | 担当 |
| --- | --- | --- |
| 進行役（管理者） | 1 | あなた。管理画面の操作、設定変更、記録 |
| 協力者 | 6 | P1〜P6。選手として操作する |

**進行役はチームに所属しない。** 無所属からの通報（UAT-G03）と、
管理者が選手を兼ねない状態での管理操作を確認するためである。

## 4.2 協力者の編成

| チーム | リーダー | メンバー |
| --- | --- | --- |
| TEAM_A | P1 | P2 |
| TEAM_B | P3 | P4 |
| TEAM_C | P5 | P6 |

**3チーム必要である。** 2チームでは、同じ相手との再戦抑止（UAT-J01）と
ランキング掲載条件（UAT-J02）を確認できない。

## 4.3 人数が足りないとき

| 集まった人数 | できること | できないこと |
| --- | --- | --- |
| 6人 | 全シナリオ | — |
| 4人 | A〜H（2人チーム×2） | J（サブアカウント対策）、C05 の3チーム同時待機 |
| 2人 | A・B・D の一部 | マッチング以降のほぼ全部 |

**1人での代替は行わない。** 本書の目的は「複数人が同時に触ったときの挙動」であり、
1人で複数アカウントを切り替えた確認は、同時操作の競合（UAT-D08）を再現できない。

## 4.4 事前に協力者へ渡すもの

1. 検証環境のURL
2. [使い方ガイド](../PlayerGuide.md)（サイトのトップページからも読める）
3. Discord アカウントが必要である旨
4. **本書は渡さない。** 期待結果を先に読むと、迷った箇所が記録に残らない

# 5. 検証環境の前提

## 5.1 環境

| 項目 | 内容 |
| --- | --- |
| 環境 | 検証環境（本番と別の Supabase プロジェクト） |
| 定期処理 | **有効であること。** `ForkGuide.md` 手順11が未実施だと、期限切れの確認がすべて失敗する |
| データ | 開始時点で空であること。過去の検証データが残っていると期待結果が変わる |

**★定期処理の稼働を必ず先に確かめる。** `matchmaker` と `auto-resolve-matches` は
毎分実行される。止まっていると「相手が見つからない」「期限が来ても何も起きない」という形で
現れ、機能の不具合と区別が付かない。確認方法は `ForkGuide.md` 11.3 にある。

## 5.2 ブラウザ

協力者には**普段使っているブラウザ**で参加してもらう。指定しない。

そのうえで、進行役は次を確認する。

| ID | 観点 | 操作 | 期待結果 |
| --- | --- | --- | --- |
| UAT-A01 | スマートフォン | 携帯電話でトップ・ランキング・マイチームを開く | 横スクロールが発生せず、ボタンが指で押せる |
| UAT-A02 | ダークモード | OSの外観設定を切り替える | 文字と背景のコントラストが保たれる |

# 6. 事前準備（進行役）

## 6.1 検証用の設定へ変える

**管理 → 設定** で次の値にする。**協力者を集める前に済ませる。**

| 設定 | 初期値 | 検証値 | 理由 |
| --- | ---: | ---: | --- |
| チーム人数の上限 | 3 | **2** | 協力者6人で3チーム作るため |
| 申告期限 | 60 | **15** | 待ち時間を現実的にする |
| 承認期限 | 60 | **10** | 同上 |
| クールダウン | 30 | **3** | 待たされる側の確認を実時間内に収める |
| 延長の長さ | 60 | **5** | 延長が効いたことを画面で見るため |
| 無応答までの経過 | 30 | **2** | 無応答による不成立を実時間内に収める |
| 応答の猶予 | 30 | **2** | 同上 |
| シーズン終了の猶予 | 10 | **2** | シーズン切替を実時間内に収める |
| 同じ相手と再戦できない長さ | 24 | **0** | 同じペアで繰り返し試すため（J章で戻す） |
| ランキング掲載の最低対戦相手数 | 3 | **0** | 序盤からランキングを確認するため（J章で戻す） |

**★期限は試合が作られた時点の設定で確定する。** 設定を変えても、
**すでに進行中の試合の期限は変わらない。** 期限の確認を行うシナリオでは、
**設定を変えてから試合を作る。** 順番を逆にすると、変えたはずの期限で終わらない。

**★シーズンの状態（マッチング停止・更新禁止・シーズン番号）はこの画面に無い。**
I章のシーズン操作だけが書き換える。

## 6.2 管理者権限を確かめる

進行役のアカウントで **管理** メニューが見えることを確認する。

見えない場合は `ForkGuide.md` 手順10（Supabase の `app_metadata` にロールを設定）を実施し、
**いったんログアウトして入り直す。** 付与は再ログインまで画面へ反映されない。

## 6.3 記録の準備

8章の記録票を人数分ではなく**シナリオ数分**用意する。記録するのは進行役である。

協力者には「詰まったらその場で声を出す」とだけ伝える。**書かせない。**
書く作業を与えると、詰まったことを報告しなくなる。

## 6.4 当日の流れ（目安3時間）

| 時間 | 内容 | 章 |
| --- | --- | --- |
| 0:00–0:15 | 集合・ログイン | A |
| 0:15–0:45 | チーム編成 | B |
| 0:45–1:15 | マッチングと基本の確定 | C・D前半 |
| 1:15–1:45 | 期限切れ・反対申告 | D後半 |
| 1:45–2:15 | 不成立・延長 | E |
| 2:15–2:35 | 閲覧・通報 | F・G |
| 2:35–2:55 | 管理機能・シーズン | H・I |
| 2:55–3:00 | 権限の境界・脱退 | K・UAT-B17〜B18 |
| （後日） | サブアカウント対策 | J |

**J章は同じ日に行わない。** 再戦抑止は時間の経過を条件にするため、
設定を戻したうえで別の日に確認する。

# 7. シナリオ

## 7.1 記載の見方

| 列 | 内容 |
| --- | --- |
| ID | `UAT-` 接頭辞つきの通し番号 |
| 観点 | 何を確かめるか |
| 実施者 | 操作する人 |
| 前提 | 開始時点で成立していること |
| 操作 | 実行すること |
| 期待結果 | 画面に現れるべきこと |

**期待結果に書かれていないことが起きたら、それは記録の対象である。**
「たぶん仕様だろう」で流さない。仕様であれば設計書に書いてあり、後から照合できる。

| --- | ---: |
| 同じ相手と再戦できない長さ | 1（時間） |
| ランキング掲載の最低対戦相手数 | 2 |

**★再戦抑止は検証のため 24 ではなく 1 にする。** 24時間では当日中に解除を確認できない。
**掲載条件は 3 ではなく 2 にする。** 3チームでは異なる相手が最大2つしか作れない。

| ID | 観点 | 実施者 | 前提 | 操作 | 期待結果 |
| --- | --- | --- | --- | --- | --- |
| UAT-J01 | 再戦の抑止 | TEAM_A・TEAM_B | 直前に A 対 B が**確定**している | 両者だけが待機する | **組まれない。** エラーも出ず、待機が続くだけ |
| UAT-J02 | 第三のチームとは組まれる | TEAM_A・TEAM_C | UAT-J01 の待機中 | TEAM_C も待機する | **A 対 C が成立する** |
| UAT-J03 | 引き分けは抑止しない | 任意の2チーム | 直前に**引き分け**で終わっている | 両者が待機する | **組まれる**（抑止の対象は確定した試合だけ） |
| UAT-J04 | 時間経過で解除 | TEAM_A・TEAM_B | UAT-J01 から1時間後 | 両者が待機する | **組まれる** |
| UAT-J05 | 掲載条件 | 誰でも | TEAM_A が1チームとだけ対戦済み | ランキングを見る | **TEAM_A が一覧に出ない** |
| UAT-J06 | 記録は残っている | P1 | 同上 | マイチームを見る | **レートと戦績は記録されている** |
| UAT-J07 | 理由が分かる | P1 | 同上 | 画面の説明を読む | **なぜ載らないのかが分かる。** 隠されていない |
| UAT-J08 | 条件を満たすと載る | 誰でも | TEAM_A が2チームと対戦済み | ランキングを見る | **自動的に載る** |
| UAT-J09 | 順位に穴が無い | 誰でも | 未掲載のチームがある状態 | 順位を見る | **1位から連番。** 飛び番が無い |
| UAT-J10 | 対戦カードは抑止されない | 進行役 | UAT-J01 の状態 | **管理 → 対戦カードを用意する** で A 対 B を作る | **作れる**（ADR-039 ②） |
| UAT-J11 | 同時在席の指標 | 進行役 | 一通り対戦した後 | **管理 → 対戦の偏り** | 同時在席の有無が出ている。指標の意味が画面で説明されている |

**★UAT-J01 は「エラーが出ないこと」が期待結果である。** 待機し続けるのが正しい挙動であり、
協力者には「壊れている」と見える。**そう見えたかどうかを記録する。**
見えたなら、それは画面の案内が足りないという発見である。

| UAT-K01 | 管理画面 | 協力者 | 一般利用者 | `/admin` `/admin/teams` `/admin/settings` `/admin/audit` `/admin/reports` `/admin/matches` `/admin/season` `/admin/integrity` をURL直打ちで開く | **すべて 403。** 中身が一切見えない |

# 8. 記録

## 8.1 判定

| 判定 | 意味 |
| --- | --- |
| OK | 期待結果のとおり |
| NG | 期待結果と違う |
| 保留 | 実施できなかった（前提が崩れた・人数不足） |
| 気付き | 期待結果どおりだが、**協力者が迷った・誤解した** |

**「気付き」を必ず設ける。** 仕様どおり動いているのに使えない箇所は、
OK/NG の二値では記録に残らない。本書の目的の半分はここにある。

## 8.2 記録票

```text
ID        : UAT-____
判定      : OK / NG / 保留 / 気付き
実施者    : 
発生時刻  : 
実際に起きたこと:

協力者の反応（原文のまま）:

再現手順（NG のときのみ）:
1.
2.
3.
```

**★協力者の言葉は言い換えない。** 「分かりにくいと言った」ではなく
「『これ押していいの？』と聞いた」と書く。言い換えると、何が分からなかったのかが消える。

## 8.3 NG が出たときの扱い

1. その場で深追いしない。**再現手順だけ取って次へ進む**
2. 後続シナリオの前提が崩れる NG のみ、進行役が回避策を決めて続行する
3. 回避したことを記録する（回避した状態で通った OK は、条件付きの OK である）

## 8.4 発生時刻を必ず書く

期限切れ・クールダウン・定期処理が絡む NG は、**時刻が無いと後から追えない。**
`audit_logs` と `cron.job_run_details` の突き合わせに要る。

# 9. 終了条件と後片付け

## 9.1 終了条件

| 条件 | 内容 |
| --- | --- |
| 必須 | J章を除く全 ID が OK / NG / 保留 のいずれかで判定されている |
| 必須 | NG のすべてに再現手順がある |
| 必須 | J 章が別日程で完了している |
| 判断 | NG と気付きを Issue へ起こすかどうかを決めている |

**「NG が0件であること」を終了条件にしない。** NG が出ないことより、
**出た NG が再現できることのほうが重要である。**

## 9.2 後片付け（進行役）

1. **設定を戻す。** とくに 6.1 で 0 にした2項目と、D-4 で 1分 にした期限
2. **保守による停止がオフであること**を確認する
3. **シーズンが通常営業に戻っていること**を確認する
4. 検証環境のデータを残すか消すかを決める（消す場合は I 章の削除操作を使う）
5. 協力者へ結果を共有する。**とくに、報告してくれたことがどう扱われたかを返す**

**★1 を忘れると、次の検証で「なぜか相手が見つからない」が起きる。**
再戦抑止と掲載条件は、切ったままだと本番と挙動が変わる（ADR-036 ⑤）。

## 9.3 本番へ持ち込まないもの

| 項目 | 理由 |
| --- | --- |
| 検証用の設定値 | 期限1分・クールダウン3分は本番の運用に耐えない |
| 再戦抑止・掲載条件の 0 | サブアカウント対策が無効になる |
| 検証中に掲示したお知らせ | 選手が本番の告知と誤認する |
