# RiskManagement.md

# リスク管理

Version: 1.0
Status: Active

---

# 1. 目的

本書は、本プロジェクトにおけるリスクの識別、評価、対応、および継続的な管理方法を定義する。

リスク管理の目的は、すべてのリスクを排除することではなく、早期に発見し、影響を最小限に抑え、適切な意思決定を支援することである。

---

# 2. 適用範囲

本書は以下を対象とする。

* プロジェクト管理
* システム設計
* ソースコード
* インフラストラクチャ
* 外部サービス
* OSSライブラリ
* AIを利用した開発
* セキュリティ
* リリース運用

---

# 3. リスク管理プロセス

リスクは以下のライフサイクルに従って管理する。

```text
リスクの識別
      ↓
リスクの評価
      ↓
優先度の決定
      ↓
対応策の策定
      ↓
継続的な監視
      ↓
クローズ
```

すべてのリスクには担当者（Owner）を設定し、定期的に見直しを行う。

---

# 4. リスク分類

リスクは以下の分類で管理する。

| 分類      | 内容                      |
| ------- | ----------------------- |
| アーキテクチャ | システム構成・設計に関するリスク        |
| 技術      | 言語・フレームワーク・ライブラリに関するリスク |
| インフラ    | CI/CD、デプロイ、クラウド環境など     |
| セキュリティ  | 認証・認可・脆弱性・秘密情報          |
| パフォーマンス | 性能・スケーラビリティ・負荷          |
| データ     | DB・マイグレーション・バックアップ      |
| 品質      | テスト・保守性・技術的負債           |
| プロジェクト  | スケジュール・工数・リソース          |
| 外部要因    | API変更、OSS更新、法的要件        |
| AI開発    | AI利用による品質・設計上のリスク       |

# 5. リスク評価

## 影響度（Impact）

| レベル      | 説明             |
| -------- | -------------- |
| Critical | プロジェクト継続が困難になる |
| High     | 主要機能へ大きな影響を与える |
| Medium   | 一部機能へ影響を与える    |
| Low      | 軽微な影響のみ        |

---

## 発生可能性（Probability）

| レベル       | 説明         |
| --------- | ---------- |
| Very High | ほぼ発生する     |
| High      | 発生する可能性が高い |
| Medium    | 発生する可能性がある |
| Low       | 発生する可能性は低い |

---

## 優先度

| 優先度 | 対応               |
| --- | ---------------- |
| P0  | 直ちに対応する          |
| P1  | 実装前に対応する         |
| P2  | 状況を監視し必要に応じて対応する |
| P3  | 受容し継続監視する        |

# 7. リスク状態

| 状態         | 説明       |
| ---------- | -------- |
| Open       | 識別済み     |
| Mitigating | 対応中      |
| Monitoring | 対応済み・監視中 |
| Closed     | 解決済み     |
| Accepted   | リスクを受容する |

---

# 8. 対応計画

各リスクについて以下を記録する。

* 発生原因
* 対応方針
* 回避策
* 暫定対応
* 完了予定日
* 担当者

---

# 9. エスカレーション

以下に該当する場合は、直ちにエスカレーションする。

* P0リスクとなった場合
* マイルストーン達成を妨げる場合
* システム構成の変更が必要となる場合
* セキュリティ問題を含む場合
* 本番環境へ影響する場合

エスカレーションされたリスクは、対応方針が決定するまで関連作業を保留する。

---

# 10. AI開発に関するリスク

AIを利用した開発では、以下のリスクに注意する。

| リスク             | 対応方法                            |
| --------------- | ------------------------------- |
| 仕様の推測（ハルシネーション） | 設計書・DecisionLogを必ず確認する          |
| Scope外の変更       | AIContextのScopeを厳守する            |
| 設計との不整合         | Project Constitutionおよび設計書を優先する |
| 不要なリファクタリング     | 必要最小限の変更に限定する                   |
| 古い仕様での実装        | 最新のDecisionLogを確認する             |

AIが生成したコードは、必ずレビューを実施する。

# 11. 技術的リスク

代表的な技術的リスクの例

* フレームワークの破壊的変更
* OSSライブラリの互換性問題
* データベースマイグレーション失敗
* 認証仕様の変更
* API互換性の破壊
* ブラウザ互換性
* 性能劣化

本番リリース前に、それぞれの対応策を確認する。

---

# 12. 運用リスク

代表的な運用リスク

* ドキュメント消失
* CI/CD障害
* リリース失敗
* バックアップ失敗
* 誤デプロイ
* 環境設定ミス

運用手順は文書化し、定期的に見直す。

---

# 13. セキュリティリスク

代表例

* シークレット情報の漏洩
* 認証不備
* 認可不備
* SQL Injection等のインジェクション攻撃
* 脆弱なOSSライブラリの利用

セキュリティリスクは、特別な理由がない限り **High以上** として扱う。

---

# 14. リスクレビュー

以下のタイミングでリスクレビューを実施する。

* マイルストーン開始前
* リリース前
* 大規模な設計変更後
* 障害発生後

必要に応じて、Closedとなったリスクを再オープンしてよい。

# 16. AI運用ルール

AIはリスクを独断で「受容」「クローズ」「優先度変更」してはならない。

AIが新たなリスクを発見した場合は、以下を報告する。

1. リスクの内容
2. 想定される影響
3. 対応案
4. 推奨事項

最終的な評価および意思決定は、プロジェクト責任者が行う。
