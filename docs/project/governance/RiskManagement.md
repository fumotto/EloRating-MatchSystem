# リスク管理

Version: 1.0
Status: Active

---

# 1. 目的

本書は、本プロジェクトにおけるリスクの識別、評価、対応、および継続的な管理方法を定義する。

リスク管理の目的は、すべてのリスクを排除することではなく、早期に発見し、影響を最小限に抑え、適切な意思決定を支援することである。

---

# 2. 適用範囲

本書は以下を対象とする。

* プロジェクト管理
* システム設計
* ソースコード
* インフラストラクチャ
* 外部サービス
* OSSライブラリ
* AIを利用した開発
* セキュリティ
* リリース運用

---

# 3. リスク管理プロセス

リスクは以下のライフサイクルに従って管理する。

```text
リスクの識別
      ↓
リスクの評価
      ↓
優先度の決定
      ↓
対応策の策定
      ↓
継続的な監視
      ↓
クローズ
```

すべてのリスクには担当者（Owner）を設定し、定期的に見直しを行う。

---

リスクは以下の分類で管理する。

| 分類      | 内容                      |
| ------- | ----------------------- |
| アーキテクチャ | システム構成・設計に関するリスク        |
| 技術      | 言語・フレームワーク・ライブラリに関するリスク |
| インフラ    | CI/CD、デプロイ、クラウド環境など     |
| セキュリティ  | 認証・認可・脆弱性・秘密情報          |
| パフォーマンス | 性能・スケーラビリティ・負荷          |
| データ     | DB・マイグレーション・バックアップ      |
| 品質      | テスト・保守性・技術的負債           |
| プロジェクト  | スケジュール・工数・リソース          |
| 外部要因    | API変更、OSS更新、法的要件        |
| AI開発    | AI利用による品質・設計上のリスク       |

# 5. リスク評価

## 影響度（Impact）

| レベル      | 説明             |
| -------- | -------------- |
| Critical | プロジェクト継続が困難になる |
| High     | 主要機能へ大きな影響を与える |
| Medium   | 一部機能へ影響を与える    |
| Low      | 軽微な影響のみ        |

---

## 発生可能性（Probability）

| レベル       | 説明         |
| --------- | ---------- |
| Very High | ほぼ発生する     |
| High      | 発生する可能性が高い |
| Medium    | 発生する可能性がある |
| Low       | 発生する可能性は低い |

---

## 優先度

| 優先度 | 対応               |
| --- | ---------------- |
| P0  | 直ちに対応する          |
| P1  | 実装前に対応する         |
| P2  | 状況を監視し必要に応じて対応する |
| P3  | 受容し継続監視する        |

## 6.1 対応方針

| ID    | 対応                                                                          |
| ----- | --------------------------------------------------------------------------- |
| R-001 | **Closed（2026-08-04）。** ADR-022 により認証プロバイダを Discord へ確定し、PoCを不要とした。スキーマはプロバイダ非依存のため変更なし |
| R-002 | Connection Pooler（Transaction mode）を使用し、prepared statement を無効化する。接続数上限を監視する |
| R-003 | Edge Function内の認可チェックを必須とし、Integration Testで全Functionを検証する（Part8）           |
| R-004 | **期限を過ぎたまま残る試合の件数**で判定する（6.1.1）。Cronの実行結果は補助情報に留める。確認は `scripts/health-check.sql`（`11_Deployment.md` 13.2） |
| R-005 | ビルド時に `404.html` を生成する。E2E（TC-E2E-038）で本番相当構成を検証する                          |
| R-006 | 接続数を監視し、必要に応じて Pooler の上限を調整する                                              |
| R-007 | 招待コードをハッシュ化して保存し、参照RLSを自チームに限定する。有効な招待は1件のみとする                              |

## 6.1.1 R-004：Cronの実行結果を判定基準にしてはならない

**当初の対策「Cronの実行結果を監視対象とする」は、本リスクを検知できない。**
2026-08-10 の健全性確認で実証した（Issue #3）。

`cron.job_run_details.status` は **SQL が実行できたこと**しか示さない。
`0015_cron.sql` の `invoke_edge_function` は Vault が未登録なら何もせずに戻るため、
Edge Function が一度も呼ばれていなくてもジョブは `succeeded` と記録される。

| 観測 | 実態 |
| -- | -- |
| Cron 4本すべて `succeeded`（毎分実行） | Edge Function の呼び出しは0回 |
| ダッシュボード上は正常 | 試合は永久に確定しない |

Vault の登録忘れという単純な設定漏れで、**本リスクが顕在化しながら気付けない**状態になる。

### 判定基準

以下を本リスクの一次指標とする。いずれも `scripts/health-check.sql` が出力する。

| 指標 | 正常 | 異常の意味 |
| -- | -- | ----- |
| `overdue_report` | 0付近 | 申告期限を過ぎた `PLAYING` が解散されていない |
| `overdue_approve` | 0付近 | 承認期限を過ぎた `WINNER_REPORTED` が自動承認されていない |
| Vault の登録 | 登録済み | 未登録なら Cron は何も呼ばない（クラウドでは異常） |

Cron の成否は、上記が異常なときに**原因を切り分けるための補助情報**として見る。

**1チームは同時に1試合しか持てない。** 試合が確定しないチームは以後どの試合にも参加できず、
放置すると滞留が単調に増える。`overdue_*` が増え続けているかどうかが決定的な兆候である。

# 9. エスカレーション

以下に該当する場合は、直ちにエスカレーションする。

* P0リスクとなった場合
* マイルストーン達成を妨げる場合
* システム構成の変更が必要となる場合
* セキュリティ問題を含む場合
* 本番環境へ影響する場合

エスカレーションされたリスクは、対応方針が決定するまで関連作業を保留する。

# 10. AI開発に関するリスク

AIを利用した開発では、以下のリスクに注意する。

| リスク             | 対応方法                            |
| --------------- | ------------------------------- |
| 仕様の推測（ハルシネーション） | 設計書・DecisionLogを必ず確認する          |
| Scope外の変更       | AIContextのScopeを厳守する            |
| 設計との不整合         | Project Constitutionおよび設計書を優先する |
| 不要なリファクタリング     | 必要最小限の変更に限定する                   |
| 古い仕様での実装        | 最新のDecisionLogを確認する             |

AIが生成したコードは、必ずレビューを実施する。

# 12. 運用リスク

代表的な運用リスク

* ドキュメント消失
* CI/CD障害
* リリース失敗
* バックアップ失敗
* 誤デプロイ
* 環境設定ミス
* **設定漏れにより自動処理が「成功したまま何もしない」状態になること**（R-004 / 6.1.1）

運用手順は文書化し、定期的に見直す。

監視指標を選ぶ際は、**その指標が「処理が行われなかったこと」を区別できるか**を確認する。
実行記録の成否は、処理が意味のある仕事をしたことを保証しない。

---

# 13. セキュリティリスク

代表例

* シークレット情報の漏洩
* 認証不備
* 認可不備
* SQL Injection等のインジェクション攻撃
* 脆弱なOSSライブラリの利用

セキュリティリスクは、特別な理由がない限り **High以上** として扱う。

# 14. リスクレビュー

* リリース前

* 障害発生後

必要に応じて、Closedとなったリスクを再オープンしてよい。

# 16. AI運用ルール

AIはリスクを独断で「受容」「クローズ」「優先度変更」してはならない。

AIが新たなリスクを発見した場合は、以下を報告する。

1. リスクの内容
2. 想定される影響
3. 対応案
4. 推奨事項

最終的な評価および意思決定は、プロジェクト責任者が行う。
